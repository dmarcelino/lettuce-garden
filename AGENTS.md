# Agents Guidance

This file provides guidance to agents when working with code in this repository.

## What this is
`lettucectl` is a Bash CLI that runs several single-user [Lettuce](https://github.com/dmarchevsky/lettuce) stacks on one host, one per person. Each stack is its own Docker Compose project behind its own Cloudflare Tunnel and Cloudflare Access application (Google login). There is no multi-user code: isolation comes from separate stacks, authentication from Cloudflare. README.md covers the design rationale; docs/operations.md and docs/cloudflare-setup.md cover operator workflows.

## Relationship to upstream
This repo composes Lettuce and adds to it: multi-user stacks plus an opinionated set of extras (MCP servers, skills, sidecars, CLI commands). Lettuce is not ours, and every departure from its design is something `lettucectl upgrade` can break.
- **Never modify Lettuce without an explicit request.** That covers the `upstream/` clone and the upstream repository (code, issues, PRs). Say when a change would fit better upstream, and stop there.
- **Plug in only through supported seams:** `stack.env`, compose profiles, the overlays in `compose/`, Lettuce's Settings and `letta connect`, the shared MCP list, the skills directory, `host.docker.internal`. A feature that needs Lettuce internals (undocumented files under `/root/.letta`, BFF routes, the app-server protocol) is redesigned, or names that dependency here so an upgrade checks it. Named today:
  - `cmd_shell`: letta-code's memory path, `$LETTA_LOCAL_BACKEND_DIR/memfs/$AGENT_ID/memory`.
  - `toolbox`: the app-server image layout, `/opt/claude-code/bin`.
  - `google_redirect_uri`: the BFF route `/api/google/oauth/callback`.
  - `find_agent`: the JSON shape of `letta agents list` (`.items[]`).
- **Overlays restrict, never redefine.** They may drop ports, drop capabilities, set `read_only` or cap resources; they don't replace an upstream service's image, entrypoint, command or internal env.
- **No second way into an agent.** The BFF owns the only connection to the app-server: no `lettucectl` command or sidecar opens another or starts a turn. `compose exec` for files and read-only CLI calls is the limit. The vault's `/secrets/` route (its own UI and Access check) is the one route that bypasses the BFF; another needs a written reason here.
- **Don't write into what Lettuce manages.** Its settings, MCP list, agent memory and workspaces are Lettuce's. Use its own mechanism where one exists; where we must write, own a namespace (as `skills` does with its manifest). Never turn an upstream feature on by editing its files: a feature is on when its profile and its Settings switch are.
- **Keep upstream's defences on.** Keep its auth settings at their strictest and never disable a boot check. Nothing secret goes under `stacks/<name>/state/`: agent shells mount it read-write as root. Don't shorten the BFF's `stop_grace_period`, which lets in-flight turns drain on a redeploy. Give new profiles names upstream is unlikely to claim: it matches tokens exactly, so a shared name turns on both.

## Commands
```bash
tests/run.sh                 # all offline tests (docker, curl, dig, gh, secret-tool are stubbed)
tests/run.sh <pattern>       # only tests whose function name contains <pattern>, e.g. tests/run.sh test_add_
shellcheck -x lettucectl lib/*.sh scripts/*.sh tests/run.sh tests/run-broker.sh tests/stubs/*
tests/run-broker.sh          # vault tests (pytest in its image's `test` stage; needs Docker)
tests/run-broker.sh -k vault   # extra args go to pytest
```
Run the first two before changing the CLI, and `tests/run-broker.sh` before changing `broker/`. The CLI has no build step; the broker image is built by `lettucectl up`.

## Layout and flow
- `lettucectl`: argument handling and the `cmd_*` functions (one per subcommand, dispatched from `main`).
- `lib/common.sh`: messages (`info`/`warn`/`die`), env-file helpers, paths, validation, the `compose` wrapper, VAPID key generation, and `check_stack`.
- `lib/cloudflare.sh`: Cloudflare API v4 via `cf_api` (curl + jq) and one `cf_*` helper per resource.
- `compose/hardening.yml`, `compose/multi.yml` and `compose/secrets.yml`: overlays merged on top of `upstream/docker/compose.yml`, in that order, for every stack. `secrets.yml` defines the `secret-broker` service behind the `secrets` profile; relative paths in it resolve against `upstream/docker`.
- `agent-skills/`: skills for every agent of every stack (a directory with `SKILL.md` each), installed by `lettucectl skills` through `compose exec` into the app-server's `/root/.letta/skills`. `using-vault-secrets` ships `vault-run`, the vault's helper (Python, standard library only).
- `broker/`: the vault (Python, MCP SDK 2.x, Starlette, `cryptography`). `crypto.py` is scrypt + AES-GCM, `vault.py` the encrypted SQLite store on the broker-only volume, `kinds.py` the secret types (public and private fields, which may be shared without asking), `service.py` agent requests, approvals and `env` delivery handles (in memory), `auth.py` the Access JWT and CSRF checks, `app.py` `/mcp`, vault-run's `/redeem` and the `/secrets/` UI. docs/secret-broker.md is the user guide and security model. Internal names (`secret-broker`, `secrets`, `/secrets/`) predate the vault and stay, so routes and volumes don't move.

Untracked instance data (never commit; see `.gitignore`): `config.env` (global settings plus cached Cloudflare ids), `.secrets/cloudflare-api-token`, `upstream/` (Lettuce clone at `LETTUCE_REF`), `stacks/<name>/stack.env` (that stack's secrets and Cloudflare ids) and `stacks/<name>/state/`.

## Key invariants
- **Env files are parsed, never sourced.** `config.env` and `stack.env` are plain `KEY=value` files that Docker Compose also reads. Use `env_get`/`env_set`/`env_unset`/`cfg`; `env_set` rewrites atomically and keeps mode 600. No quotes or inline comments in these files.
- **`stack.env` is the state record for `add` and `remove`.** `cmd_add` creates resources in a fixed order (Access policy -> Access app -> tunnel -> tunnel token -> tunnel ingress -> DNS CNAME) and stores each id as soon as it exists, so a re-run resumes where it stopped. `CF_DNS_RECORD_ID` being set means the stack is complete. `cmd_remove` deletes in reverse and unsets each id only on success, so it can be retried. Preserve this when adding steps; tests assert the exact call order.
- **All docker compose calls go through `compose NAME ...`.** It runs under `env -i` (so the caller's shell can't override `stack.env`), with project `lettuce-<name>`, `--project-directory upstream/docker`, the four compose files in order, and an explicit `--env-file`.
- **`check_stack` gates every `up`.** It refuses: `stack.env` not mode 600, any `DEV_BYPASS_*` (bypasses Access), required keys empty, short `SESSION_SECRET`, `COMPOSE_PROFILES` without `cloudflared` or different from `config.env` `PROFILES` (all stacks share one app-server image), any published port in the rendered config, `DISABLE_AUTOUPDATER != 1` on app-server/channel-gateway (letta-code would reinstall itself over the pinned version), and with the `secrets` profile a `secret-broker` that is missing, not `read_only`, without `cap_drop: [ALL]`, with a host mount, or whose volume another service mounts (`check_broker`). New safety rules belong here.
- **Profiles change everywhere at once.** `cmd_profiles` runs `check_stack --skip-profiles` on every stack before writing, then writes `config.env` `PROFILES` and every `stack.env` `COMPOSE_PROFILES` together and runs `up` on each. Unchanged lists skip all of that. It always removes `stale_services` (containers whose profile is off; Compose leaves them running), comparing what exists rather than what changed, so re-runs repair interrupted ones. Don't tell operators to edit the profile lists by hand.
- **Google redirect URIs are manual.** Google has no API for an OAuth client's redirect URIs, so with the `google` profile `add` and `profiles` print each stack's URI and `remove` reminds the operator to delete it (`google_redirect_uri`, `google_reminder`).
- **The Cloudflare API token never goes in argv.** `cf_api` passes it to curl as a config block on stdin; a test checks this.
- **Access policy and `ALLOWED_USERS` change together** (`cmd_users`); upstream requires them to stay in sync.
- **VAPID keys are generated once per stack** (`ensure_push_keys`) and never rotated: a new keypair invalidates every browser push subscription. The BFF (`PUSH_VAPID_*`) and the vault (`BROKER_VAPID_*`) each have their own pair.
- **Tunnel routes follow the profiles.** `cf_tunnel_configure` puts `^/secrets(/|$)` -> `secret-broker:8000` before the app-server rule when the stack has `secrets`; `add` sets it, and `profiles` re-applies every stack's routes on every run, before `up`.
- **The vault is the approval gate, not Lettuce.** Agents share the BFF's network namespace and can call the vault directly, so approval and every `/secrets/` page require a verified Access JWT (`auth.py`). Agents read names and public fields in `list_secrets`, and get private values only through `request_secret`: after the user approves those fields, or for secrets the user set to share without asking (only kinds with `auto_allowed`). With `delivery: "env"` the agent gets a handle instead of the values; `vault-run` redeems it at `/redeem` (single use, `HANDLE_TTL_SECONDS`, at most `MAX_HANDLES` unused, `secret-broker` host and no `Origin` only; a lock drops handles and uncollected values) and scrubs the values from the command's output. That keeps values out of the conversation but is not a boundary: agents are root in the app-server and can redeem a handle themselves, so docs must not claim more. Never add an MCP tool that edits secrets or bypasses approval, never write vault data, keys or the passphrase to disk unencrypted or to logs, and never mount `secret-broker-data` into another service. The data key exists only in memory while unlocked; agent activity must not extend the auto-lock.
- Upstream version moves only via `lettucectl upgrade <tag>`: Lettuce tags pin the letta-code server version the UI was compiled against.
- Use `lettucectl restart`, not a single-service restart: the BFF shares the app-server's network namespace.
- **`toolbox` keeps the operator's credentials out of the stack.** It is a `docker run` of the stack's app-server image with one agent's workspace, never a `compose exec`: agents share the app-server as root. Tokens go through docker's environment as `-e NAME`, never argv. The image's inherited `com.docker.compose.*` labels are emptied, or Compose and `stale_services` would count the toolbox as a stack container. `~/.config/lettucectl/toolbox` is parsed, never sourced.
- **Only `skills` installs agent skills, and only replaces its own.** The in-container script (`SKILLS_INSTALL`) removes what its manifest (`.lettucectl-skills`) lists and leaves upstream's and Settings' skills alone; `up` does not sync. Names must not match upstream's `docker/agent-skills` (the BFF rewrites those on every connect). Skill text is public and lands in every operator's stacks: keep it generic.

## Sensitive and personal data
This repo is public and every operator runs it against their own Cloudflare account, domain and users. Nothing tracked may identify a real deployment.
- Never commit secrets: API tokens, tunnel tokens, `SESSION_SECRET`, VAPID private keys, passwords, or any value copied out of `config.env`, `stack.env` or `.secrets/`. This also covers test fixtures, docs, commit messages and PR descriptions.
- Never commit personal or deployment-specific values: real email addresses, names, domains or hostnames, Cloudflare account/zone/app/tunnel/record ids, IP addresses, or local paths such as `/home/<user>/...`.
- Use the existing placeholders instead: stack names `alfred`/`hal`, agent name `lucius`, emails like `alfred@gmail.com` or `hal@example.com`, domains under `example.com`/`example.org`, and the canned stub ids (`acc1`, `zone1`, `tun1`, ...).
- When pasting command output, logs or rendered compose config into docs, tests or issues, redact real values first.
- Before committing, review the staged diff for these values. If a new kind of instance file appears, add it to `.gitignore` rather than committing it.

## Tests
`tests/run.sh` copies the repo into a temp dir per test and puts `tests/stubs/{docker,curl,dig,gh,secret-tool}` first on `PATH`. Because `lettucectl` runs docker under `env -i`, stubs read their settings from `$T/stub.env` (written with `stub KEY=value`), not the environment.
- curl stub: logs `curl METHOD PATH BODY` to `calls.log`, answers with canned ids (`acc1`, `zone1`, `pol1`, `app1`/`aud1`, `tun1`/`tuntok1`, `rec1`); `STUB_CF_FAIL="METHOD /path"` forces a failure. Unknown routes fail, so add a route when adding an API call.
- docker stub: `compose config --format json` returns `$T/compose-config.json`, which tests overwrite to simulate rendered configs. `compose config --services` lists `app-server`, `bff` and the services of each profile in the `--env-file`'s `COMPOSE_PROFILES`, like upstream. `docker ps -a --filter label=com.docker.compose.project=...` answers from `$T/containers.txt` lines of `project service` (helper: `containers NAME SERVICE...`). `letta agents list` (inside `compose exec`) answers from `$T/agents.json` (helper: `agents NAME...`, ids `agent-1`, `agent-2`, ...) and swallows stdin like the real thing; any other `exec` appends its stdin to `$T/exec-stdin.log`, saves its `sh -c` script to `$T/exec-script` (so tests can run it on a temp dir) and exits with `STUB_EXEC_RC`. `image inspect` answers a Compose-built image's config (fails with `STUB_IMAGE_RC`), and `run` writes the value of each `-e NAME` to `$T/run-env.log`, so tests can tell env-passed values from argv.
- dig stub: answers from `$T/dns.txt` lines of `name TYPE answer`.
- gh and secret-tool stubs: print `STUB_GH_TOKEN` and `STUB_SECRET_TOOL`, or fail like a logged-out tool. Toolbox tests run with `HOME=$T/u` (helper `tb`), so the real home is never read.
- Helpers: `ctl` (runs lettucectl, sets `$RC`, output in `$OUT`), `ok_rc`/`bad_rc`, `out_has`/`out_lacks`, `log_has`/`log_lacks`, `calls`, `body_of`, `senv`, `eq`, `added` (a fresh `alfred` stack). Each test is a `test_*` function run under `set -e`, so a failing assert ends it.
- With the `secrets` profile, `check` needs a `secret-broker` in `$T/compose-config.json`: call `broker_config` (before `added`) or `with_secrets` (after it).
- Vault tests (`broker/tests`, pytest) never use the network: `FakeSender` (push), `make_jwt` with a test RSA key, `FAST_KDF` (cheap scrypt), a fake `Clock`, and fake values (`TEST_SECRET_DO_NOT_USE_938742`, a card number, a street) that tests assert never reach the vault file on disk, logs, pushes or pages before Show. `test_vault_run.py` runs `agent-skills/using-vault-secrets/vault-run` against a loopback stub of `/redeem`; `tests/run-broker.sh` mounts `agent-skills/` into the test container for it.
