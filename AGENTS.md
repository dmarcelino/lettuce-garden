# Agents Guidance

This file provides guidance to agents when working with code in this repository.

## What this is
Lettuce Garden is an opinionated, batteries-included way to run [Lettuce](https://github.com/dmarchevsky/lettuce) for several people on one host: one isolated stack per person behind Cloudflare Access, plus extras such as a secrets vault, Gmail triggers, a code editor, an egress proxy, MCP servers and agent skills. `lettucectl`, a Bash CLI, runs the single-user stacks, one per person. Each stack is its own Docker Compose project behind its own Cloudflare Tunnel and Cloudflare Access application (Google login). There is no multi-user code: isolation comes from separate stacks, authentication from Cloudflare. README.md covers the design rationale; docs/operations.md and docs/cloudflare-setup.md cover operator workflows.

## Relationship to upstream
This repo composes Lettuce and adds to it: multi-user stacks plus an opinionated set of extras (MCP servers, skills, sidecars, CLI commands). Lettuce is not ours, and every departure from its design is something `lettucectl upgrade` can break.
- **Never modify Lettuce without an explicit request.** That covers the `upstream/` clone and the upstream repository (code, issues, PRs). Say when a change would fit better upstream, and stop there.
- **Plug in only through supported seams:** `stack.env`, compose profiles, the overlays in `compose/`, Lettuce's Settings and `letta connect`, the shared MCP list, the skills directory, `host.docker.internal`. A feature that needs Lettuce internals (undocumented files under `/root/.letta`, BFF routes, the app-server protocol) is redesigned, or names that dependency here so an upgrade checks it. Named today:
  - `cmd_shell`: letta-code's memory path, `$LETTA_LOCAL_BACKEND_DIR/memfs/$AGENT_ID/memory`.
  - `toolbox`: the app-server image layout, `/opt/claude-code/bin`.
  - `google_redirect_uri`: the BFF route `/api/google/oauth/callback`.
  - `find_agent`: the JSON shape of `letta agents list` (`.items[]`).
  - `compose/pipelock-proxy.yml`: who follows `HTTPS_PROXY`. letta-code runs on the Node of letta-code's own `docker/Dockerfile` (22.19 today), which ignores it even with `NODE_USE_ENV_PROXY=1`; Node >= 22.21 follows it, so on every `upgrade` check `node --version` in the app-server: once it is >= 22.21, letta-code's own traffic goes through pipelock too, and `NO_PROXY` must still cover what it calls inside the stack. `NO_PROXY` is a hand-kept list of service names: a service agents or the executor call inside the stack (a new garden sidecar, a new upstream service) goes in it, or pipelock refuses its private address. searxng documents only `outgoing.proxies` and follows the variables only because its client (curl_cffi) defaults to `trust_env`; ddg-mcp uses httpx and curl_cffi, which do too.
  - `gmail-triggers` executor (`gmail-triggers/executor/run.mjs`): `letta cron add` with `--name=`, `--description=`, `--prompt=`, `--at=in 1m`, `--once`, `--agent=`, `--conversation=new|default` (the `=` form, since letta-code's strict `parseArgs` misreads a value starting with `-`) and its JSON output (`.id`); `letta agents list` (`.items[]`); the scheduler picking up a changed task file without a restart; the app-server entrypoint copying `/root/.letta/system-cron` to `/etc/cron.d`; the image's `/usr/local/bin/agent-env` (upstream's documented way to give a cron job PID 1's environment, `node` included).
  - `doc-tools` (docs/doc-tools.md): how `letta mcp call` runs a stdio server from Settings -> MCP (started per call in the app-server, in the calling agent's cwd; only `HOME`, `PATH`, `SHELL`, `TERM`, `USER`, `LOGNAME` and the entry's `env` passed, so no `PWD`; stdin closed, then SIGTERM, then SIGKILL 2 s apart; 60 s per request; stderr piped and never read; a bare `tools`/`search` starts every stdio server); the shared MCP list's file for `lettucectl mcp` (`/root/.letta/mcp-home/.letta/settings.json`: one `agentId: agent-local-mcp-global` entry in `agents` whose `mcpServers` every `letta mcp` call reads; rendered whole by the BFF, which reads it from disk before every change and shows what is there; a stdio entry with no args or env passes its validation); the `mcp-servers` skill wrapper `/root/.letta/skills/mcp-servers/scripts/mcp.sh` (named in the `working-with-documents` skill); workspaces at `/work/<agent-id>`; `/opt/lettuce-doc-tools` free in the app-server image; an app-server with glibc >= 2.28 and system ICU (OfficeAgent), and a `/tmp` that allows exec.
  - `code-server-exec` (`code-server/exec/`, docs/code-server.md): built `FROM` the app-server's image (`additional_contexts: base: service:app-server`), so it depends on that image being Debian with `apt` (it installs `openssh-server`), `bash` as root's shell, the image `ENV` that points `PATH`, `NPM_CONFIG_PREFIX`, `CARGO_HOME`, `GOBIN` and the `UV_*` variables at `/opt/agent-tools`, and `/usr/local/bin/agent-env` reading PID 1's environment (`init: true`; its own comment says "Cron only", and the editor's terminal is its second user); the workspaces at `$LETTA_STATE_DIR/workspaces` and the tools at `$LETTA_STATE_DIR/tools`, mounted as the app-server mounts them.
  - the `/garden/` landing page's agent list (`garden-common/src/garden_common/static/landing-agents.js`, with the code editor on): Lettuce's browser WebSocket `/ws` on the stack's origin (the BFF mints its session from the Access JWT on the upgrade and checks `Origin`), its `__bff_hello` frame first, then `agent_list` (in the BFF's `ALLOWED_SESSION_COMMANDS`) sent as `{"type": "agent_list", "request_id": ..., "query": {"limit": 100}}`, answered by a frame carrying that `request_id` with `success` and `agents[]` of `id` and `name` (or a `__bff_error` with it); a session that never sends `__bff_watching` holds back no push notifications. Also code-server's `?folder=` query and the workspaces at `/work/<agent-id>`.
- **Overlays restrict, never redefine.** They may drop ports, drop capabilities, set `read_only` or cap resources; they don't replace an upstream service's image, entrypoint, command or internal env. Two exceptions. `compose/pipelock-proxy.yml` adds the standard proxy variables (and `NODE_USE_ENV_PROXY`) to app-server, ddg-mcp and searxng so their outbound traffic passes pipelock. Upstream sets none of them, and they change where traffic goes, not what the services do. `compose/doc-tools.yml` adds a read-only image mount at `/opt/lettuce-doc-tools` and a second network to the app-server: stdio MCP servers can only run inside it, and the image keeps one copy of the tools per host; it replaces nothing upstream sets. Another needs a written reason here.
- **No second way into an agent.** The BFF owns the only connection to the app-server: no `lettucectl` command or sidecar opens another or starts a turn. `compose exec` for files and read-only CLI calls is the limit. The one exception is a garden sidecar starting a turn through letta-code's own scheduler: `gmail-triggers` hands a request to its executor in the app-server, which runs `letta cron add --once`. It opens no connection, the scheduler fires the task on the BFF's connection, and it gives agents nothing new, since they can already run `letta cron add` themselves. Only `gmail-triggers` uses it: the sidecar issues requests only for rules the person made on its Access-protected page, within each rule's hourly limit (the executor runs whatever well-formed request it is served, and agents can read its token, which gives them nothing `letta cron add` doesn't). Three features bypass the BFF, each with its own UI and Access check: the vault's `/garden/secrets/`; `/garden/gmail-triggers/`, because trigger rules must live where agents can't edit them (inside Lettuce, they could); and `/garden/code-server/`, the code editor, because a person needs the workspaces' files and a terminal from anywhere, which Lettuce has no UI for; it opens no connection to the app-server or the BFF and starts no turn, and its terminal is a separate container no stronger than an agent. `/garden/` itself, the landing page linking to them, is served by the first of those sidecars that is on, behind the same Access check. Another needs a written reason here; garden sidecars go under `/garden/<sidecar>/`.
- **Don't write into what Lettuce manages.** Its settings, MCP list, agent memory and workspaces are Lettuce's. Use its own mechanism where one exists; where we must write, own a namespace (as `skills` does with its manifest). The one write into the MCP list is `lettucectl mcp` (`lib/mcp-servers.mjs`): there is no supported way to set it across stacks, so it owns the entries whose command is under `/opt/lettuce-doc-tools/`, adds them once per stack, and refuses a file of any other shape. Never turn an upstream feature on by editing its files: a feature is on when its profile and its Settings switch are.
- **Keep upstream's defences on.** Keep its auth settings at their strictest and never disable a boot check. Nothing secret goes under `stacks/<name>/state/`: agent shells mount it read-write as root. Don't shorten the BFF's `stop_grace_period`, which lets in-flight turns drain on a redeploy. Give new profiles names upstream is unlikely to claim: it matches tokens exactly, so a shared name turns on both.

## Commands
```bash
tests/run.sh                 # all offline tests (docker, curl, dig, gh, secret-tool are stubbed)
tests/run.sh <pattern>       # only tests whose function name contains <pattern>, e.g. tests/run.sh test_add_
shellcheck -x lettucectl lib/*.sh scripts/*.sh pipelock/entrypoint.sh tests/run.sh tests/run-sidecar.sh tests/run-pipelock.sh tests/stubs/* doc-tools/bin/* doc-tools/lib/launch.sh code-server/editor/bin/* code-server/editor/entrypoint.sh code-server/editor/tests/test.sh
tests/run-sidecar.sh broker            # vault tests (pytest in its image's `test` stage; needs Docker)
tests/run-sidecar.sh broker -k vault   # extra args go to pytest
tests/run-sidecar.sh gmail-triggers    # sidecar tests, plus the executor's (node --test in node:22.22.0-slim) when no args are given
tests/run-sidecar.sh code-server       # the code editor's gate (pytest), plus the editor image's tests when no args are given
node --test 'gmail-triggers/executor/tests/*.test.mjs'   # executor tests on the host
tests/run-pipelock.sh                  # the pipelock image and config against a real pipelock (needs Docker, not the internet)
node --test tests/mcp-servers.test.mjs # lib/mcp-servers.mjs against temp settings files
node --test garden-common/tests/landing-agents.test.mjs # the landing page's agent list against a fake page and /ws
tests/run-sidecar.sh doc-tools         # the PDF MCP's tests (pytest in the doc-tools image's `test` stage, Debian 12 like the app-server)
```
Run the first two before changing the CLI, and `tests/run-sidecar.sh <dir>` before changing `broker/`, `gmail-triggers/`, `code-server/`, `garden-common/` (which all three use; plus `node --test garden-common/tests/landing-agents.test.mjs` for its landing script) or `doc-tools/`, and `tests/run-pipelock.sh` before changing `pipelock/`. `scripts/doc-tools-e2e.sh` runs the document tools against the real app-server image and a real Gotenberg (needs Docker and the internet for the first build; throwaway containers only). `scripts/code-server-e2e.sh [--browser]` runs the code editor's real images (the gate's checks against the real editor, the terminal's way into the shell, the editor's isolation) and, with `--browser`, drives the workbench in Chromium against a workspace planted with what an agent could write (Playwright's image; same rules). The CLI has no build step; the sidecar images are built by `lettucectl up`. CI (`.github/workflows/ci.yml`) runs all of these on every branch push and by hand (Actions, "Run workflow"); a new test script or linted file goes there too.

## Layout and flow
- `lettucectl`: argument handling and the `cmd_*` functions (one per subcommand, dispatched from `main`).
- `lib/common.sh`: messages (`info`/`warn`/`die`), env-file helpers, paths, validation, the `compose` wrapper, VAPID key generation, and `check_stack`.
- `lib/mcp-servers.mjs`: adds or removes the document tools in a stack's Settings -> MCP (Node, no dependencies; run in the app-server by `lettucectl mcp`, `add`, `up` and `profiles`).
- `lib/cloudflare.sh`: Cloudflare API v4 via `cf_api` (curl + jq) and one `cf_*` helper per resource.
- `compose/hardening.yml`, `compose/multi.yml`, `compose/secrets.yml`, `compose/gmail-triggers.yml`, `compose/pipelock.yml` and `compose/code-server.yml`: overlays merged on top of `upstream/docker/compose.yml`, in that order, for every stack. `secrets.yml` defines the `secret-broker` service behind the `secrets` profile, `gmail-triggers.yml` the `gmail-triggers` service behind its profile, `pipelock.yml` the `pipelock` service behind its profile, `code-server.yml` the code editor's three services, networks and volumes behind the `code-server` profile; relative paths in them resolve against `upstream/docker`. `compose/doc-tools.yml` follows only with the `doc-tools` profile: the app-server's image mount and network (a profile can't gate a mount). `compose/pipelock-proxy.yml` comes last and only with the `pipelock` profile: it sets the proxy variables on app-server, ddg-mcp and searxng (a profile can't gate an environment variable, and the `pipelock` service itself must stay defined so `stale_services` can remove it). `compose/shared/gotenberg.yml` is not a stack overlay: it is the host's one Gotenberg, the Compose project `lettuce_shared` (`compose_shared`).
- `pipelock/`: the image of the egress proxy (pipelock, built from source at a pinned tag without the `enterprise` build tag, so Apache-2.0 only), its config (`pipelock.yaml`, baked into the image) and its entrypoint, which generates the receipt signing key on the `pipelock-data` volume once. docs/egress-firewall.md is the guide and its limits.
- `doc-tools/`: the document tools' image (`Dockerfile`, final stage `FROM scratch`: OfficeAgent's pinned, SHA-256-checked Linux build, a standalone CPython and a venv from the hash-pinned `requirements.lock`), the launchers `bin/officeagent` and `bin/pdf-mcp` (with `lib/launch.sh`: workspace from `pwd -P`, HOME and caches under `/tmp`, no core dumps; OfficeAgent's content root pinned to the image, so a workspace `appsettings.json` is never read), OfficeAgent's `office/config.json`, and the PDF MCP (`src/pdf_mcp`, Python, MCP SDK 2.x `MCPServer` over stdio, PyMuPDF + pypdf + httpx): `paths.py` the workspace jail (component-wise `O_NOFOLLOW` opens from a root fd, temp file then rename, sources never overwritten), `ops.py` the in-process operations, `gotenberg.py` the client (uploads only, never URLs; conversions, merge, rotate, watermark and stamp), `server.py` the twelve tools. docs/doc-tools.md is the guide and security model.
- `backup/`: the Dockerfile of the image `lettucectl backup` copies with (Debian slim plus rsync).
- `agent-skills/`: skills for every agent of every stack (a directory with `SKILL.md` each), installed by `lettucectl skills` through `compose exec` into the app-server's `/root/.letta/skills`. `using-vault-secrets` ships `vault-run`, the vault's helper (Python, standard library only).
- `broker/`: the vault (Python, MCP SDK 2.x, Starlette, `cryptography`). `crypto.py` is scrypt + AES-GCM, `vault.py` the encrypted SQLite store on the broker-only volume, `kinds.py` the secret types (public and private fields, which may be shared without asking), `service.py` agent requests, approvals and `env` delivery handles (in memory), `app.py` `/mcp`, vault-run's `/redeem`, the `/garden/secrets/` UI (`PREFIX` in `config.py`) and the `/garden/` landing page. docs/secret-broker.md is the user guide and security model. Internal names (`secret-broker`, the `secrets` profile) predate the vault and stay, so profiles and volumes don't move.
- `garden-common/`: Python code the garden sidecars share: `auth.py` (the Access JWT and CSRF checks, and `check_fetch`: pages load only as top-level documents, forms post and the vault's `fetch()` calls come only from the same origin, by Fetch Metadata; `COOP` for every garden response), `static/garden.css` (Lettuce's look with the colours reversed; both sidecars' pages use it) and `garden.py` (the `/garden/` landing page, which every sidecar serves through `landing_routes`, behind the Access check alone and without touching the sidecar: it links to `/garden/<profile>/` for each profile in `GARDEN_PROFILES`; `LABELS` names them; with `code-server` on, its one script, `static/landing-agents.js`, inline and allowed by its hash in the page's own CSP (`landing_csp`, `connect-src` only `wss://<stack>/ws`), lists the agents from Lettuce, each a link to `/garden/code-server/?folder=/work/<agent-id>`, names as text only). Images install it from the `garden-common` build context (`additional_contexts` in the overlays, `--build-context` in `tests/run-sidecar.sh`); it is not on PyPI, so it is never a pip dependency by name.
- `gmail-triggers/`: Gmail triggers (Python, Starlette, httpx), the first garden sidecar. It polls Gmail with the Google token Lettuce stores (read-only), keeps rules and pending requests in `$LETTA_STATE_DIR/garden/gmail-triggers` (its only bind mount; not mounted in the app-server), and serves `/garden/gmail-triggers/` (pages, behind Access) plus `/executor/v1/` (for its executor, bearer token, never routed by the tunnel). `executor/run.mjs` (Node, no dependencies) runs in the app-server from system cron every minute: it fetches pending requests from `http://gmail-triggers:8000/executor/v1/`, turns each into a one-off task with `letta cron add`, and posts back the results, the agent list and a heartbeat. docs/gmail-triggers.md is the user guide and security model; docs/gmail-triggers-plan.md the design record.
- `code-server/`: the code editor (docs/code-server.md; docs/code-server-plan.md the design record). The directory itself is the gate (Python, Starlette, httpx, websockets), a garden sidecar at `/garden/code-server/` and the only way to the editor, which listens only on a Unix socket (`/run/code-server/editor.sock` on the `code-server-sock` volume, which only the gate, read-only, and the editor mount; no port, since code-server has no Access check of its own): the Access JWT on every request and WebSocket (closed when the JWT expires; this stack's `Origin` only), `Sec-Fetch-Site: same-origin` for anything but a read, a prefix that is not spelled out refused, `Vary: Sec-Fetch-Dest` on every answer, the prefix stripped and put back on redirects, request and response header allow-lists (never `Cookie`, the Access JWT, `Set-Cookie` or COOP; `Service-Worker-Allowed` narrowed to the prefix), and only the workbench and code-server's own frames loaded as pages (everything else `nosniff` and `CSP: sandbox`). `editor/` is the editor's image: code-server pinned by version and SHA-256 per architecture, built-in extensions pruned to `extensions-kept`, the fixed `settings.json` whose keys its entrypoint puts back whole over the person's on every start (code-server then runs with umask 022), the SSH keys it makes once on its own volumes, and `bin/exec-shell`, the terminal profile (a notice, then `ssh -tt` into the shell through `agent-env`); its `tests/test.sh` runs in the image's `test` stage. `exec/` is the shell's image: the app-server's image plus `openssh-server` (`sshd_config`: the editor's key only, nothing forwarded); it starts once the editor is healthy (its socket and the keys exist). `tests/e2e/` holds what `scripts/code-server-e2e.sh` runs in the gate's test image and in Chromium.

Untracked instance data (never commit; see `.gitignore`): `config.env` (global settings plus cached Cloudflare ids), `.secrets/cloudflare-api-token`, `upstream/` (Lettuce clone at `LETTUCE_REF`), `stacks/<name>/stack.env` (that stack's secrets and Cloudflare ids) and `stacks/<name>/state/`.

## Key invariants
- **Env files are parsed, never sourced.** `config.env` and `stack.env` are plain `KEY=value` files that Docker Compose also reads. Use `env_get`/`env_set`/`env_unset`/`cfg`; `env_set` rewrites atomically and keeps mode 600. No quotes or inline comments in these files.
- **`stack.env` is the state record for `add` and `remove`.** `cmd_add` creates resources in a fixed order (Access policy -> Access app -> tunnel -> tunnel token -> tunnel ingress -> DNS CNAME) and stores each id as soon as it exists, so a re-run resumes where it stopped. `CF_DNS_RECORD_ID` being set means the stack is complete. `cmd_remove` deletes in reverse and unsets each id only on success, so it can be retried. Preserve this when adding steps; tests assert the exact call order.
- **All docker compose calls go through `compose NAME ...`.** It runs under `env -i` (so the caller's shell can't override `stack.env`), with project `lettuce-<name>`, `--project-directory upstream/docker`, the seven compose files in order (plus `compose/doc-tools.yml`, then `compose/pipelock-proxy.yml`, when that env file's `COMPOSE_PROFILES` has `doc-tools` or `pipelock`), and an explicit `--env-file`. With `doc-tools` it also passes `DOC_TOOLS_TAG` (`doc_tools_tag`, a hash of `doc-tools/` without its tests) and `DOC_TOOLS_NETWORK` (`lettuce-doc-tools-<name>`) through `env -i`: lettucectl computes them, and they are never written to `stack.env` (`compose_env ENV_FILE NAME ...` is the same with another env file, for `check_stack --profiles`).
- **`check_stack` gates every `up`.** It refuses: `stack.env` not mode 600, any `DEV_BYPASS_*` (bypasses Access), required keys empty, short `SESSION_SECRET`, `COMPOSE_PROFILES` without `cloudflared` or different from `config.env` `PROFILES` (all stacks share one app-server image), any published port in the rendered config, `DISABLE_AUTOUPDATER != 1` on app-server/channel-gateway (letta-code would reinstall itself over the pinned version), app-server or any service with `network_mode: service:app-server` keeping `NET_RAW` (agents could capture the Access JWT the vault accepts), and with the `secrets` profile a `secret-broker` that is missing, not hardened (`check_hardened`: not `read_only`, without `cap_drop: [ALL]`, `privileged`, with `cap_add`, `network_mode`, `pid`, `ipc`, `volumes_from` or `devices`), or with a host mount (`check_sidecar`). Whatever the profiles (both volumes outlive their profile), `secret-broker-data` mounted by anything but `secret-broker`, `pipelock-data` by anything but `pipelock`, `google-creds` mounted by anything but `bff`, `google-mcp` and `gmail-triggers`, and any `volumes_from` naming `gmail-triggers`, `secret-broker`, `pipelock` or a service that mounts `google-creds`, `secret-broker-data` or `pipelock-data` (it would copy their mounts). With `pipelock`: a `pipelock` service that is missing, not hardened (`check_hardened`) or with a host mount (`check_sidecar`); an app-server whose `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY` or `http_proxy` is not `http://pipelock:8888`, or whose `NO_PROXY` or `no_proxy` lacks `secret-broker` or `gmail-triggers` (pipelock must never see the vault's values or the executor's token) (`check_pipelock`). A profile whose dependency is off (`profile_unmet`: `gmail-triggers` needs `google`), also checked by `profiles` before writing. With `gmail-triggers`: a missing or malformed `GMAIL_TRIGGERS_EXECUTOR_TOKEN`; a `gmail-triggers` service that is missing, not hardened (`check_hardened`), with any bind mount but `$LETTA_STATE_DIR/garden/gmail-triggers:/data`, with `google-creds`/`google-policy` writable or any other named volume; another service bind-mounting `$LETTA_STATE_DIR/garden`, a path under it or a parent of it (also after resolving symlinks at check time), or a volume whose `driver_opts` point there (relative bind devices are refused outright); `$LETTA_STATE_DIR`, `state/garden` or `state/garden/gmail-triggers` being a symlink (Docker would follow it on the host) (`check_gmail_triggers`). Whatever the profiles, a service other than the app-server with an image mount or a `lettuce-doc-tools` source. With `doc-tools`: an app-server whose mount at `/opt/lettuce-doc-tools` is not this tree's image read-only, that lacks `default` or `doc-tools` among its networks, another service on `doc-tools`, a `doc-tools` network that is not the external `lettuce-doc-tools-<name>`, or (when it exists) not internal with lettucectl's label for that stack, and Docker < 28 or Compose < 2.35 (`check_doc_tools`); and before `sync_doc_tools` starts Gotenberg, a rendered shared Gotenberg that is not hardened (`check_hardened`), runs as root or without `no-new-privileges`, publishes a port, mounts anything, sits on a non-internal network, lacks any of the flags that stop documents fetching URLs or sets one back to `false`, or sets an allow-list, disabled web security or debug logging (`check_gotenberg`). With `code-server` (`check_code_server`): the gate not a hardened sidecar (`check_sidecar`), on a network other than `default` or mounting anything but `code-server-sock` read-only at `/run/code-server`; the editor not hardened (`check_hardened`), with a host path other than `$LETTA_STATE_DIR/workspaces:/work`, named volumes other than `code-server-data:/data`, `code-exec-keys:/keys` and `code-server-sock:/run/code-server`, a network other than `code-exec`, a command without each of `--socket /run/code-server/editor.sock`, `--auth none`, `--disable-proxy`, `--extensions-dir /opt/lettuce-editor/no-extensions` and `--user-data-dir /data/user` exactly once in the `--flag value` form (code-server takes the last of a repeated flag), or with `--bind-addr`, `--socket-fd`, `--disable-workspace-trust`, `--link`, `--proxy-domain`, `--trusted-origins`, `--enable-proposed-api`, `--install-extension`, `--github-auth`, `--builtin-extensions-dir` or `--abs-proxy-base-path`, or `EXTENSIONS_GALLERY` other than `{}`; the shell not isolated (`check_isolated`: privileged, `cap_add`, `network_mode`, `pid`, `ipc`, `volumes_from`, devices), keeping `NET_RAW`, with host paths other than the workspaces at `/work` and the tools at `/opt/agent-tools`, a named volume other than `code-exec-keys` read-only, or networks other than `code-exec` and `code-egress`; anyone else on `code-exec` or `code-egress`; `code-exec` not internal; `$LETTA_STATE_DIR`, `workspaces` or `tools` a symlink. Whatever the profiles, `code-server-data` mounted by anything but `code-server-editor`, `code-exec-keys` by anything but the editor and the shell, `code-server-sock` by anything but the gate and the editor, `volumes_from` naming one of the three code editor services or a service mounting their volumes, and a `network_mode` sharing one of their network namespaces (`service:` or a `container:` name with `code-server` in it). Like every check, these run at `up`: a container Docker restarts on its own (daemon restart, reboot) is not re-checked. `volume_users` is the shared "who mounts this volume" helper. New safety rules belong here.
- **Profiles change everywhere at once.** `cmd_profiles` runs `check_stack NAME --profiles NEW` on every stack before writing (it renders the config from a temporary copy of `stack.env` with the new list, through `compose_env ENV_FILE NAME ...`, so every check, the gmail-triggers ones included, sees the new list), then writes `config.env` `PROFILES` and every `stack.env` `COMPOSE_PROFILES` together and runs `up` on each. Unchanged lists skip all of that. It always removes `stale_services` (containers whose profile is off; Compose leaves them running), comparing what exists rather than what changed, so re-runs repair interrupted ones. Don't tell operators to edit the profile lists by hand.
- **Google redirect URIs are manual.** Google has no API for an OAuth client's redirect URIs, so with the `google` profile `add` and `profiles` print each stack's URI and `remove` reminds the operator to delete it (`google_redirect_uri`, `google_reminder`).
- **The Cloudflare API token never goes in argv.** `cf_api` passes it to curl as a config block on stdin; a test checks this.
- **Access policy and `ALLOWED_USERS` change together** (`cmd_users`); upstream requires them to stay in sync.
- **lettucectl owns the stack's Access application's settings.** `cf_app_body` is the one definition: `add` posts it (`cf_app_create`), and `route_stack` puts it back on every `profiles` run (`cf_app_update`; a `PUT` replaces the application's settings, so a change made in the dashboard does not survive). Its cookie is HttpOnly (no script on the stack's origin, the code editor's tab included, can read the Access token and hand it to an agent) and SameSite=Lax. `check` does not read it back: it runs offline.
- **VAPID keys are generated once per stack** (`ensure_push_keys`) and never rotated: a new keypair invalidates every browser push subscription. The BFF (`PUSH_VAPID_*`) and the vault (`BROKER_VAPID_*`) each have their own pair.
- **Tunnel routes follow the profiles.** `cf_tunnel_configure` puts each route of `PROFILE_ROUTES` (`lib/cloudflare.sh`) whose profile the stack has before the app-server rule: `^/garden/secrets(/|$)` -> `secret-broker:8000`, then `^/garden/gmail-triggers(/|$)` -> `gmail-triggers:8000`, then `^/garden/code-server(/|$)` -> `code-server:8000`, then `^/garden/?$` (the landing page) -> the first of those added; with none of them on, `/garden/` stays Lettuce's. A new garden sidecar adds a row (its page at `/garden/<profile>/`, which a test checks), an entry in `LABELS` (`garden-common/src/garden_common/garden.py`) and `landing_routes`. `up` writes `GARDEN_PROFILES` in `stack.env` (`sync_garden_profiles`): the profiles of `PROFILE_ROUTES` that are on, in its order, which the overlays pass to the sidecars. Never pass them `COMPOSE_PROFILES` itself: any profile change would then recreate them, and recreating the vault locks it. `add` sets them, and `profiles` re-applies every stack's routes on every run, before `up`.
- **The vault is the approval gate, not Lettuce.** Agents share the BFF's network namespace and can call the vault directly, so approval and every `/garden/secrets/` page require a verified Access JWT (`auth.py`). It is the same JWT cloudflared sends the BFF in plain HTTP inside that namespace, so every container there drops `NET_RAW` (`compose/hardening.yml`). An agent could still bind the BFF's port while the BFF is down and the app-server is not; only a separate Access application for the vault would close that. Agents read names and public fields in `list_secrets`, and get private values only through `request_secret`: after the user approves those fields, or for secrets the user set to share without asking (only kinds with `auto_allowed`). Values shared as text always come with `rules` (`service.rules`): approved purpose only, no outside service unless the purpose needs it, never repeated in a reply, memory or files. Those are instructions, not a boundary. With `delivery: "env"` the agent gets a handle instead of the values; `vault-run` redeems it at `/redeem` (single use, `HANDLE_TTL_SECONDS`, at most `MAX_HANDLES` unused, `secret-broker` host and no `Origin` only; a lock drops handles and uncollected values) and scrubs the values from the command's output. That keeps values out of the conversation but is not a boundary: agents are root in the app-server and can redeem a handle themselves, so docs must not claim more. Never add an MCP tool that edits secrets or bypasses approval, never write vault data, keys or the passphrase to disk unencrypted or to logs, and never mount `secret-broker-data` into another service (only `backup`'s one-off container may, read-only). The data key exists only in memory while unlocked; agent activity must not extend the auto-lock.
- Upstream version moves only via `lettucectl upgrade <tag>`: Lettuce tags pin the letta-code server version the UI was compiled against.
- Use `lettucectl restart`, not a single-service restart: the BFF shares the app-server's network namespace.
- **`toolbox` keeps the operator's credentials out of the stack.** It is a `docker run` of the stack's app-server image with one agent's workspace, never a `compose exec`: agents share the app-server as root. Tokens go through docker's environment as `-e NAME`, never argv. The image's inherited `com.docker.compose.*` labels are emptied, or Compose and `stale_services` would count the toolbox as a stack container. `~/.config/lettucectl/toolbox` is parsed, never sourced. The agents' tools (`state/tools`) are mounted at `/opt/agent-tools` only with `--tools`, read-only unless `--tools=rw`, and a missing directory is refused rather than created by docker.
- **`backup` reads the state only through its own container.** A `docker run` of `lettuce-backup:local` (`backup/Dockerfile`, built with plain `docker build`, so it carries no Compose labels) with `--init` (so Ctrl-C reaches rsync), `--network none`, a read-only root, `cap_drop ALL` plus CHOWN/DAC_OVERRIDE/FOWNER, and the state, `stack.env`, vault volume and pipelock volume mounted read-only. The destination may not be inside this repo (it is public, and backups hold secrets). Snapshots are written as the operator (`--chown`), hard-linked to the previous one (`--link-dest`), and renamed from `.partial-<TS>` only when complete, so `--link-dest` and `--keep` never pick a broken one. A `flock` on `<dir>/<name>/.lock` keeps a second run from deleting the first one's `.partial-*`. The vault and pipelock's receipts are copied whenever their volume exists, whatever the profiles; check `volume inspect` before mounting one, since `run -v` creates missing volumes. A running stack is copied only after `--pause`, `--live` or the operator's answer, and the EXIT trap that unpauses it is set before pausing. With `all`, each stack runs in its own subshell and a failure does not stop the rest.
- **The code editor runs nothing agents wrote.** It shares the stack's origin with Lettuce and the vault, and code-server serves webviews from that origin, so whatever runs in the editor's container runs as the person. The editor stays in Restricted Mode for good (no startup prompt, banner always on; only `vscode.typescript-language-features` is allowed in it, through the application-scoped `extensions.supportUntrustedWorkspaces`, and terminals, through `terminal.integrated.allowInUntrustedWorkspace`): tasks, debugging and a workspace's terminal settings need trust, and nothing else turns tasks off. No built-in extension that starts processes, provides tasks, debugs, renders workspace content in a webview, signs in anywhere, or asks for trust, but the Markdown preview: the editor's Dockerfile pins its security level to Strict (its own policy then allows no script but the preview's own; "Disable" would drop the policy) and removes the Markdown Editor, and both edits fail the build when a release no longer matches them; VS Code's git extension asks to trust each repository's folder before opening it, so it is out and git runs in the terminal. No marketplace, nothing installable, no `node` on `PATH`, an empty `/etc/shells`, no port (code-server listens only on the socket only the gate mounts, so the shell, where agents' code runs, can't reach it), no network but the shell's. Every terminal is `ssh -tt` into `code-server-exec`, the shell, which is as strong as an agent and no stronger: not on the stack network, no Access or Google token, no credentials. The person can still choose "Trust" (running a task asks), and code-server keeps that in the browser: the docs say never. A new kept extension or setting is checked with `scripts/code-server-e2e.sh --browser`, whose planted workspace must run nothing in the editor.
- **The garden pages refuse same-origin script.** Every garden page checks Fetch Metadata (`check_fetch`): pages only as top-level documents (any site, for the Access re-login redirect), form posts only from the same origin, the vault's JSON calls only from its own script; a refusal renders without the person's email, since pages carrying it carry the form token. Stylesheets, scripts, icons and the manifest are assets (`asset=True`) and stay unchecked. The landing page's only script is its agent list, inline and allowed by hash; it reads Lettuce's `/ws` as the person and sends nothing but `agent_list`. Every garden response, the gate's own included, sets COOP same-origin; the editor's never do.
- **The `gmail-triggers` executor is installed by `up`, only through `compose exec`, and only replaces its own.** `sync_executor` runs after `compose up`: with the profile on it streams a tar of `gmail-triggers/executor/run.mjs` (tests excluded) and the stack's `GMAIL_TRIGGERS_EXECUTOR_TOKEN` (as a 0600 file in the tar, never argv) to the in-container script `GARDEN_INSTALL`. That replaces `/root/.letta/garden/gmail-triggers/bin/run.mjs` and the token `/etc/lettuce-garden/gmail-triggers-token` (0600, in the container layer, so not under `state/` and not in backups; `up` reinstalls it after every recreate) atomically (dot temp file, then `mv -f`), and writes the cron file `lettuce-garden-gmail-triggers` (no dot: cron skips those; it runs `node` through `agent-env`) to `/root/.letta/system-cron` and `/etc/cron.d`. An incomplete stream changes nothing. With the profile off it uninstalls when the host shows an install (bin or the system-cron file), skipping a stopped stack, whose next `up` removes it. `profiles` re-syncs the executor on every running stack on every run, so a re-run repairs a failed install; a failed install makes `up`/`profiles` fail at the end, not in the middle. `GMAIL_TRIGGERS_EXECUTOR_TOKEN` is generated once per stack whatever the profiles (`ensure_executor_token`, next to `ensure_push_keys` in `up` and `profiles`) and never rotated by itself; uninstall removes the installed copy. The executor fetches the agent list only when the sidecar's `/requests` answer sets `agents_wanted` (no list yet, older than 15 minutes, or the form was opened since).
- **Sidecar and executor share no directory.** A bind source inside `letta-home` would be agent-writable, and an agent could swap a component for a symlink that Docker follows on the host. They talk over HTTP on the stack network instead. Agents can read the executor's token (they are root in the app-server), so they can read, claim or forge what the executor sees; the token keeps out the other containers, not agents. Both sides treat the other's data as untrusted, the executor runs `letta` with an argument array, never a shell (one request failing doesn't stop the batch), and a claimed request is never offered twice (a lost turn beats a duplicate). `/executor/v1/` sits outside the tunnelled prefix and also refuses `Origin` and Cloudflare's `cf-access-jwt-assertion`, `cf-connecting-ip` and `cf-ray` headers, so nothing from the internet or a browser reaches it.
- **Pipelock is advisory, and docs must say so.** The stack network keeps its direct route: letta-code (until its Node follows `HTTPS_PROXY`), the BFF, the vault, google-mcp and gmail-triggers connect directly, and any agent can unset the variable. There is no TLS interception, so for HTTPS pipelock sees only the host name: it checks destinations (blocklist, private addresses, data hidden in host names, rates) and signs a receipt per decision, but scans content only for pages fetched through its `/fetch` endpoint (the `fetching-web-pages` skill), where `pipelock.yaml` turns prompt injection from balanced mode's log-only warning into a block (`tests/run-pipelock.sh` checks it). Its signing key and receipts live only on `pipelock-data` (generated once by its entrypoint, never rotated by lettucectl); nothing else mounts it but `backup`'s and `receipts`' one-off containers, read-only. Making it a boundary needs an internal network, which waits for letta-code's Node.
- **lettucectl owns the doc-tools image and networks; Compose only uses them.** `up_stack` (after `check_stack`) builds `lettuce-doc-tools:<hash>` with plain `docker build` when it is missing (shared by every stack, never run, only mounted) and creates the stack's network `lettuce-doc-tools-<name>` (`--internal`, label `lettuce.doc-tools.stack=<name>`), which `compose/doc-tools.yml` declares `external`, so `down`, `down -v`, `restart` and network recreation never touch it. `sync_doc_tools` runs at the end of `add`, `up` and every `profiles` run, comparing what exists: with the profile on, it starts the shared Gotenberg (`compose_shared up -d`, after `check_gotenberg`), connects it with the alias `gotenberg` to every complete stack's network it is not on yet, only when that network is internal and labelled for that stack (a network of that name made by hand is refused and Gotenberg disconnected from it), and deletes labelled networks whose stack is gone, removed or without the profile; with it off, it takes Gotenberg down and deletes every labelled network. Failures are collected and fail the command at the end ("run the same command again"). `remove` deletes the stack's network after `compose down -v` (force-disconnecting Gotenberg, which stays for the others), and `--purge` renders the stack without `doc-tools` (`env_without_profile`), so it needs neither the image nor the network. The shared project is `lettuce_shared`: an underscore can't be in a stack name, so a stack called `shared` (`lettuce-shared`) never matches it.
- **`mcp` registers the document tools in Settings -> MCP once per stack, and only those.** `lib/mcp-servers.mjs` is streamed into the app-server (`compose exec -T app-server node --input-type=module - add|remove FILE`, the script on stdin) and touches only entries whose command is under `/opt/lettuce-doc-tools/`: it adds `office` and `pdf` when missing (a same-named server with another command is the person's and stays), refuses a file of any other shape, writes a temp file renamed only when the original is unchanged, and reads the file back after 2 s to catch an overwrite by the BFF (up to 4 tries). On a new stack it waits up to 90 s for the BFF to create the file. Success sets `DOC_TOOLS_MCP_REGISTERED=1` in `stack.env`, and `mcp` skips a marked stack unless `--force`, so a server the person removed stays removed. `add` registers a new stack's servers after `sync_doc_tools`; `profiles` and `up` never register. With the profile off, `up` and every `profiles` run remove the registered entries of each marked stack (a stdio server that cannot start breaks every unfiltered `letta mcp tools` call) and clear the mark; a failure keeps the mark, so the next run retries. `add`/`profiles` say whether each stack is registered or print the entries and `lettucectl mcp <name>` (`doc_tools_reminder`).
- **Only `skills` installs agent skills, and only replaces its own.** The in-container script (`SKILLS_INSTALL`) removes what its manifest (`.lettucectl-skills`) lists and leaves upstream's and Settings' skills alone; `up` does not sync. Names must not match upstream's `docker/agent-skills` (the BFF rewrites those on every connect). Skill text is public and lands in every operator's stacks: keep it generic.

## Sensitive and personal data
This repo is public and every operator runs it against their own Cloudflare account, domain and users. Nothing tracked may identify a real deployment.
- Never commit secrets: API tokens, tunnel tokens, `SESSION_SECRET`, VAPID private keys, passwords, or any value copied out of `config.env`, `stack.env` or `.secrets/`. This also covers test fixtures, docs, commit messages and PR descriptions.
- Never commit personal or deployment-specific values: real email addresses, names, domains or hostnames, Cloudflare account/zone/app/tunnel/record ids, IP addresses, or local paths such as `/home/<user>/...`.
- Use the existing placeholders instead: stack names `alfred`/`hal`, agent name `lucius`, emails like `alfred@gmail.com` or `hal@example.com`, domains under `example.com`/`example.org`, and the canned stub ids (`acc1`, `zone1`, `tun1`, ...).
- When pasting command output, logs or rendered compose config into docs, tests or issues, redact real values first.
- Before committing, review the staged diff for these values. If a new kind of instance file appears, add it to `.gitignore` rather than committing it.

## Tests
`tests/run.sh` copies the repo into a temp dir per test and puts `tests/stubs/{docker,curl,dig,gh,secret-tool}` first on `PATH`. Because `lettucectl` runs docker under `env -i`, stubs read their settings from `$T/stub.env` (written with `stub KEY=value`), not the environment.
- curl stub: logs `curl METHOD PATH BODY` to `calls.log`, answers with canned ids (`acc1`, `zone1`, `pol1`, `app1`/`aud1`, `tun1`/`tuntok1`, `rec1`) (and takes `PUT /accounts/acc1/access/apps/app1`, the application update); `STUB_CF_FAIL="METHOD /path"` forces a failure. Unknown routes fail, so add a route when adding an API call.
- docker stub: `compose config --format json` returns `$T/compose-config.json`, which tests overwrite to simulate rendered configs. `compose config --services` lists `app-server`, `bff` and the services of each profile in the `--env-file`'s `COMPOSE_PROFILES`, like upstream. `docker ps -a --filter label=com.docker.compose.project=...` answers from `$T/containers.txt` lines of `project service` (helper: `containers NAME SERVICE...`). `letta agents list` (inside `compose exec`) answers from `$T/agents.json` (helper: `agents NAME...`, ids `agent-1`, `agent-2`, ...) and swallows stdin like the real thing; any other `exec` appends its stdin to `$T/exec-stdin.log`, saves its `sh -c` script to `$T/exec-script` and the arguments after it, NUL-separated, to `$T/exec-args` (so tests can run it on a temp dir: `run_exec_script ROOT [STDIN]` replays it with `/root/.letta` and `/etc/cron.d` under ROOT; `exec_args` prints the arguments) and exits with `STUB_EXEC_RC`. `compose config --services` lists `gmail-triggers` and `pipelock` for their profiles, and `code-server`, `code-server-editor` and `code-server-exec` for `code-server`. `image inspect` answers a Compose-built image's config (fails with `STUB_IMAGE_RC`), and `run` writes the value of each `-e NAME` to `$T/run-env.log`, so tests can tell env-passed values from argv. `run` also saves its `sh -c` script to `$T/run-script`, creates the `.partial-*` it is given in the directory mounted at `/dst` (like the backup copy), and exits with `STUB_RUN_RC` (or 1 when its arguments contain `STUB_RUN_FAIL`, only the first `STUB_RUN_FAIL_TIMES` times when that is set; stub values can't hold spaces, since `stub.env` is sourced). `compose ps --status running --services` counts every `$T/containers.txt` container of the project as running; `volume inspect` exits with `STUB_VOLUME_RC` (or 1 for a volume named in `STUB_VOLUMES_MISSING`), and `compose pause` with `STUB_PAUSE_RC`.
- dig stub: answers from `$T/dns.txt` lines of `name TYPE answer`.
- gh and secret-tool stubs: print `STUB_GH_TOKEN` and `STUB_SECRET_TOOL`, or fail like a logged-out tool. Toolbox tests run with `HOME=$T/u` (helper `tb`), so the real home is never read.
- Helpers: `ctl` (runs lettucectl, sets `$RC`, output in `$OUT`), `ok_rc`/`bad_rc`, `out_has`/`out_lacks`, `log_has`/`log_lacks`, `calls`, `body_of`, `senv`, `eq`, `added` (a fresh `alfred` stack). Each test is a `test_*` function run under `set -e`, so a failing assert ends it.
- `config --format json` also logs the `COMPOSE_PROFILES` of the env file it read as a `docker-env-file` line in `calls.log`. Gmail-trigger helpers: `state_elsewhere` (a `LETTA_STATE_DIR` outside `stacks/`), `installed_up` (a running stack with the executor installed), `partial_stream` (an installer tar missing a file).
- With the `secrets` profile, `check` needs a `secret-broker` in `$T/compose-config.json`: call `broker_config` (before `added`) or `with_secrets` (after it). Likewise `pipelock_config` / `with_pipelock` for `pipelock` (they also set the app-server's proxy variables), and `triggers_config` / `with_triggers` for `gmail-triggers` (they also place a placeholder `gmail-triggers/executor/run.mjs` in the test's copy); `config_edit` applies a jq filter to the rendered config, and `triggers_refused FILTER MESSAGE` asserts `check` refuses the edited config with that message.

Executor tests (`gmail-triggers/executor/tests`, `node --test`) use a local `node:http` server playing the sidecar and a `PATH` holding a fake `letta` that records its argv.

They assert the clean page passes, the injection and the private address get a 403, the injection's receipt is a signed block, and the chain verifies.
