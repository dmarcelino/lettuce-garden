# code-server

The code editor: VS Code in the browser ([code-server](https://github.com/coder/code-server)) on a stack's agent workspaces, at `https://<name>-garden.<domain>/code-server/`. This folder is three images. The folder itself is the gate (`garden-code-server`, the Python package `code_server_gate`), the only way to the editor. `editor/` is the editor (`garden-code-server-editor`). `exec/` is the shell (`garden-code-server-exec`), where terminals and Source Control's git run. All three are behind the `garden-code-server` profile. For users and admins (using it, running it, the security model): [docs/code-server.md](../docs/code-server.md); the design record is [DESIGN.md](DESIGN.md).

![The code editor's containers, networks, volumes and what they reach](../docs/diagrams/code-server-architecture.svg)

An interactive version, [code-server-architecture.html](../docs/diagrams/code-server-architecture.html), opens in a browser from a clone of this repo.

## Files

| Path | What it does |
|---|---|
| `Dockerfile`, `pyproject.toml` | The gate's image: Python 3.12 slim, `garden-common` from its build context, pinned dependencies, a `test` stage; runs as uid 65534 on port 8000. |
| `src/code_server_gate/config.py` | Settings from the environment; `PREFIX` (`/code-server`) and `EDITOR_SOCKET` (`/run/code-server/editor.sock`). |
| `src/code_server_gate/app.py` | The gate: the Access JWT on every request and WebSocket, Fetch Metadata, the prefix, request and response header allow-lists, which responses may load as pages, and the HTTP and WebSocket proxy over the editor's socket. |
| `src/code_server_gate/__main__.py` | Starts uvicorn; keeps httpx and access logs off, since the editor's URLs carry file paths. |
| `src/code_server_gate/templates/error.html` | The gate's own error page (no script). |
| `tests/` | Gate tests (pytest): `FakeEditor` plays the editor over `httpx.MockTransport` and a fake WebSocket peer. |
| `tests/e2e/` | Run by `scripts/code-server-e2e.sh`, not by pytest: `check_gate.py` (the gate against the real editor), `serve_gate.py` (the gate as cloudflared would feed it, for `--browser`) and `browser_check.py` (drives the workbench in Chromium). |
| `editor/Dockerfile` | code-server pinned by version and SHA-256 per architecture; built-in extensions pruned to `extensions-kept`; the Markdown preview pinned to Strict and its Markdown Editor removed; the git extension's two trust calls resolved to true; no git, no `node` on `PATH`, an empty `/etc/shells`, `exec-shell` as root's login shell. Each edit fails the build when a release no longer matches. |
| `editor/entrypoint.sh` | On every start: makes the SSH keys once, rewrites `authorized_keys` and `known_hosts`, puts the fixed settings back over the person's, removes a stale socket, sets `SHELL` and `VSCODE_CLI=1`, then runs code-server with umask 022. |
| `editor/settings.json` | The fixed settings: Restricted Mode for good, the two extensions allowed in it, `git.path`, the terminal profiles. |
| `editor/config.yaml` | The read-only config file code-server reads (`--config`) instead of one on its volume. |
| `editor/extensions-kept` | The allow-list of built-in extensions, with why the rest are left out. |
| `editor/ssh_config` | The SSH client: one host, the editor's key, the pinned host key, nothing forwarded, one shared connection. |
| `editor/bin/exec-shell` | The terminal profile: prints the notice, then `ssh -tt` into the shell, in the open folder (or `/work`), through `agent-env`. |
| `editor/bin/shell-git` | `git.path`: runs each git call over SSH in the shell, in the same folder (or `/`), passing on `GIT_OPTIONAL_LOCKS`; opens the shared connection once under a lock. |
| `editor/tests/test.sh` | The editor image's tests, run in its `test` stage with fake `ssh`, `agent-env` and code-server. |
| `exec/Dockerfile` | The shell: `FROM base` (the app-server's image) plus `openssh-server`, running `sshd -D`. |
| `exec/sshd_config` | Key login as root only, keys from `/keys`, nothing forwarded, no environment accepted, `MaxSessions 64`. |

## How it plugs in

- **Overlay:** `compose/code-server.yml`, merged for every stack; it adds nothing without the profile.

  | Service | Networks | Mounts | Hardening |
  |---|---|---|---|
  | `garden-code-server` (gate) | `default` | `code-server-sock` at `/run/code-server`, read-only | read-only root, no capabilities, uid 65534 |
  | `garden-code-server-editor` | `code-exec` | `$LETTA_STATE_DIR/workspaces` at `/work`, `code-server-data` at `/data`, `code-exec-keys` at `/keys`, `code-server-sock` at `/run/code-server` | read-only root, no capabilities, root (agents write the workspaces as root), no port |
  | `garden-code-server-exec` (shell) | `code-exec`, `code-egress` | `$LETTA_STATE_DIR/workspaces` at `/work`, `$LETTA_STATE_DIR/tools` at `/opt/agent-tools` (both read-write, as in the app-server), `code-exec-keys` at `/keys`, read-only | Docker's default capabilities minus `NET_RAW`, `init: true`; starts once the editor is healthy (its socket and `authorized_keys` exist) |

  `code-exec` is internal; `code-egress` is the shell's only way out, directly, not through pipelock.
- **Request path:** the tunnel sends `^/code-server(/|$)` on the garden host to the gate on port 8000 (`PROFILE_ROUTES` in `lib/cloudflare.sh`). The gate strips the prefix and talks to `http://garden-code-server-editor` over the Unix socket (httpx for HTTP, `websockets` for WebSockets), with `X-Forwarded-Host` set to the garden host; it puts the prefix back on redirects.
- **Terminals and git:** `exec-shell` and `shell-git` run `ssh -F /opt/lettuce-editor/ssh_config garden-code-server-exec` over `code-exec`; the remote command is `cd` into the folder, then `agent-env`, so the shell gets the container's `PATH` and package managers.
- **Environment:** the gate reads `CF_ACCESS_TEAM_DOMAIN`, `CF_ACCESS_AUD` (set from `CF_GARDEN_AUD`), `CF_ACCESS_ISSUER`, `ALLOWED_USERS` and `PUBLIC_ORIGIN` (set from `GARDEN_ORIGIN`). The editor gets `EXTENSIONS_GALLERY={}` (no marketplace). Nothing new goes in `stack.env`.
- **The garden:** with this profile on, the landing page ([garden/](../garden/README.md)) lists the agents, each a link to `/code-server/?folder=/work/<agent-id>`, and `sync_executor` installs the garden executor to send it the agent list.
- **lettucectl:** `up` builds the three images. `check_stack` runs `check_code_server` when the profile is on, and whatever the profiles refuses another service mounting `code-server-data`, `code-exec-keys` or `code-server-sock`, or sharing one of the three services' network namespaces; `check_garden_audience` holds the gate to the garden's Access application. In short: the gate a hardened sidecar on `default` with only the socket volume, read-only; the editor hardened, on `code-exec` only, with its exact mounts and the command-line flags that matter exactly once (and none of the ones that would open it up); the shell isolated, without `NET_RAW`, with its exact mounts and networks; nobody else on `code-exec` or `code-egress`; `code-exec` internal; no symlinks on the way to the workspaces or tools. The full list is under [What `check_code_server` refuses](#what-check_code_server-refuses).

## Build and test

```bash
tests/run-sidecar.sh code-server            # the gate's pytest, plus the editor image's tests when no args are given
scripts/code-server-e2e.sh [--browser]      # the real images: the gate against the real editor, the terminal's way into the shell,
                                            # the editor's isolation; --browser drives the workbench in Chromium (needs Docker)
shellcheck -x code-server/editor/bin/* code-server/editor/entrypoint.sh code-server/editor/tests/test.sh
```

`lettucectl up` builds the images; there is no other build step. Run `tests/run-sidecar.sh code-server` before changing this folder, and `scripts/code-server-e2e.sh --browser` before keeping a new built-in extension or setting. Moving to a new code-server release is described under [Maintaining](#maintaining).

The gate's tests use a `FakeEditor`: an `httpx.MockTransport` for HTTP (a fresh stream per response) and an echoing fake WebSocket peer, with the vault's `make_jwt` pattern and an injectable clock for the JWT's expiry. The editor image's tests (`editor/tests/test.sh`) swap `ssh` for a fake that records the remote command, replay it with `bash -c` against fake `agent-env` and `env`, and swap code-server for a fake before running the entrypoint. `tests/e2e/` holds what `scripts/code-server-e2e.sh` runs in the gate's test image and in Chromium.

### Checking it in a browser
`scripts/code-server-e2e.sh --browser` (Docker, the app-server image, and the internet for the first build) runs the real images and drives the workbench in Chromium: it plants what an agent could in a workspace (a terminal profile, an automatic task, its own TypeScript and `tsserver` node, a `tsconfig` plugin, `git.path`, a repository with a `core.fsmonitor` and a pre-commit hook), opens the folder, a TypeScript file and a terminal, types a command, commits a change from Source Control and asks to run a task. Opening the folder, the terminal and Source Control and committing must ask nothing; nothing planted may run in the editor; what is typed, the repository's `fsmonitor` and its hook must run in the shell; running a task must ask for trust.

## Rules
The guarantees and limits, in plain language, are in [docs/code-server.md](../docs/code-server.md#security-model). This is how each is kept. Before keeping a new built-in extension or setting, run `scripts/code-server-e2e.sh --browser`: its planted workspace must run nothing in the editor.

The editor shares its address (origin) with the vault and Gmail triggers: the stack's garden address, `<name>-garden.<your-domain>`, not Lettuce's. Whatever runs on that origin acts there as the person, and only the garden pages' own checks (Fetch Metadata, Cross-Origin-Opener-Policy, the form token) keep it from approving a vault request or changing a trigger. Lettuce's address is the same *site*, so Lettuce's SameSite=Lax sign-in cookies still go with requests from the editor's tab (see "What this does not cover" in [the guide](../docs/code-server.md#security-model)). And code-server, by design, serves its webviews from its own origin, so any code in its extension host can open a page that runs there. So the design rests on one rule: **nothing an agent wrote ever runs in the editor's container.**

- **The editor never trusts a workspace.** VS Code runs tasks, debug sessions and a workspace's terminal settings only in a trusted workspace; there is no other switch for tasks, and `tasks.json` decides where a task runs. The editor's settings keep every workspace in Restricted Mode (no startup prompt, the banner always on) and allow three things there (the application-scoped `extensions.supportUntrustedWorkspaces` for `vscode.typescript-language-features` and `vscode.git`, and `terminal.integrated.allowInUntrustedWorkspace`): the TypeScript extension, which then uses only its bundled TypeScript and bundled plugins (a workspace's own TypeScript, Node or `tsconfig` plugins need trust), terminals, which go to the shell container, and the git extension, whose git runs there too (below). The person can still choose "Trust" in a dialog (running a task asks); code-server keeps that choice in the browser, so the editor can't undo it. That is the one way left for agents' code to reach the editor, and why the guide says never.
- **Nothing in the editor can run or install code.** Its image keeps an allow-list of code-server's built-in extensions (`code-server/editor/extensions-kept`): none that start processes or provide tasks (npm, grunt, gulp, jake, PHP validation, terminal suggestions, tunnels), no debugger, none that render workspace content in webviews (notebooks, the profile viewer, Simple Browser) but the Markdown preview, which is held to its Strict policy (no script but its own, no frames or objects; agents' HTML is shown, never run): the image pins it, so the preview's security picker can't turn the policy off, and removes the Markdown Editor, a richer webview VS Code itself opens in Restricted Mode only after an "Open Anyway"), none that sign in anywhere (Copilot, GitHub, Microsoft), and none that ask for trust. There is no marketplace (`EXTENSIONS_GALLERY={}`), the extensions directory is read-only and empty, the image has no `node` on `PATH`, no git, no compilers and no shells for VS Code to offer as terminal profiles, and the fixed settings come back whole on every restart, with nothing added inside them. code-server reads only the image's own config file (`--config`), so no file on the editor's volume can turn on what `lettucectl check` refuses on the command line.
- **Source Control's git runs in the shell container.** A repository's own config runs code (`core.fsmonitor`, filters, `diff.external`, hooks), even for `git status`, which is why VS Code's git extension asks to trust each repository's folder before opening it; a trusted folder would also run its tasks and terminal settings in the editor. Here the extension's `git.path` is the fixed `/opt/lettuce-editor/bin/shell-git` (a machine setting, which a workspace can't change), which runs each git command over SSH in `garden-code-server-exec`, in the same folder (a command from outside `/work` runs in `/`, where there is no repository), where the repository's config runs with an agent's rights. The editor has no git of its own to fall back on. So the image makes the extension's `requestResourceTrust` and `isResourceTrusted` calls resolve to true, removing that trust prompt (the build fails when either no longer matches exactly once), and the editor stays in Restricted Mode. What git prints (file and branch names, commit messages, diffs) is text agents wrote, shown by the workbench like file content (see "What this does not cover" in [the guide](../docs/code-server.md#security-model)). The extension also reads files under `.git` itself, in the editor; an agent could point one at an editor file with a symlink and have its contents passed to git in the shell, but the editor holds nothing secret (its SSH key logs in only to the shell). When Source Control cancels a git command (a newer `git status` replaces an older one), only the editor's side stops: the command itself still runs to the end in the shell.
- **Nothing reaches the editor but the gate.** code-server has no sign-in of its own here, so it listens on no port at all: only on a Unix socket on a volume that only the gate (read-only) and the editor mount. Its one network leads to the shell, and only the editor connects over it: the shell, where agents' code runs whenever you run it in the terminal, has nothing on the editor to connect to.
- **The terminal runs in the shell container.** Its profile is an SSH session into `garden-code-server-exec`, in the open folder, and so is the editor's login shell and `SHELL`, which VS Code falls back to when no setting names a profile (a new Settings Profile starts with none), through upstream's `agent-env` (so the agents' `PATH` and package managers apply). The shell is built on the app-server's image and mounts the workspaces and `/opt/agent-tools` as the app-server does: it is as strong as an agent and holds nothing an agent can't get. No Access token, no Google token, no credentials, not the stack network (it can't reach Lettuce, the vault or the other sidecars), and only the editor can log in (key login; the editor holds the client key on its own volume). It can reach the internet, directly: pipelock does not cover it.
- **The gate is the only way in.** A `/code-server` prefix that is not spelled out (percent-encoded, say) is refused. Every request and WebSocket under `/code-server/` needs a verified Access JWT of the garden's application, the same check the vault makes; WebSockets also need the garden's own `Origin` and close when the sign-in expires (code-server reconnects, which needs a current sign-in), and anything but a read must come from the garden's own pages (`Sec-Fetch-Site: same-origin`): your other stacks share the sign-in cookie's site, not its origin. The gate passes on only listed request and response headers: the editor never sees `Cookie` (the Access cookie or Lettuce's session cookie) or the Access JWT, and can never send `Set-Cookie` or an opener policy; `Service-Worker-Allowed` is narrowed to `/code-server/`. Only the workbench and code-server's own frames may load as pages; every other response (an agent's HTML or SVG file, say) is served `nosniff` with `Content-Security-Policy: sandbox`, so it can't become a page on the origin, and every answer varies with how it was requested (`Vary: Sec-Fetch-Dest`), so the browser's cache never hands a file to a page load the gate refused. The port proxy is off.
- **The garden pages' own checks still apply.** Every garden response, the gate's own included, sets COOP same-origin; the editor's never do ([garden-common](../garden-common/README.md#rules)).

### What `check_code_server` refuses
With the profile on, `check_stack` refuses:
- **the gate** not a hardened sidecar (`check_sidecar`), on a network other than `default`, or mounting anything but `code-server-sock` read-only at `/run/code-server`;
- **the editor** not hardened (`check_hardened`); with a host path other than `$LETTA_STATE_DIR/workspaces:/work`; with named volumes other than `code-server-data:/data`, `code-exec-keys:/keys` and `code-server-sock:/run/code-server`; or on a network other than `code-exec`;
- **the editor's command** without each of `--socket /run/code-server/editor.sock`, `--auth none`, `--disable-proxy`, `--extensions-dir /opt/lettuce-editor/no-extensions`, `--user-data-dir /data/user` and `--config /opt/lettuce-editor/config.yaml` exactly once, in the `--flag value` form (code-server takes the last of a repeated flag). `--config` is the image's own, read-only; code-server would otherwise read and write one on `code-server-data`;
- **the editor's command** with any of `--bind-addr`, `--socket-fd`, `--disable-workspace-trust`, `--link`, `--proxy-domain`, `--trusted-origins`, `--enable-proposed-api`, `--install-extension`, `--github-auth`, `--builtin-extensions-dir` or `--abs-proxy-base-path`, or `EXTENSIONS_GALLERY` other than `{}`;
- **the shell** not isolated (`check_isolated`: privileged, `cap_add`, `network_mode`, `pid`, `ipc`, `volumes_from`, devices), keeping `NET_RAW`, with host paths other than the workspaces at `/work` and the tools at `/opt/agent-tools`, a named volume other than `code-exec-keys` read-only, or networks other than `code-exec` and `code-egress`;
- anyone else on `code-exec` or `code-egress`, `code-exec` not internal, or `$LETTA_STATE_DIR`, `workspaces` or `tools` a symlink.

Whatever the profiles, it refuses `code-server-data` mounted by anything but `garden-code-server-editor`, `code-exec-keys` by anything but the editor and the shell, `code-server-sock` by anything but the gate and the editor, a `volumes_from` naming one of the three services or a service mounting their volumes, and a `network_mode` sharing one of their network namespaces (`service:`, or a `container:` name with `code-server` in it).

## Maintaining
Moving code-server to a new release: change `CODE_SERVER_VERSION` and both `SHA256_*` in `code-server/editor/Dockerfile` (GitHub shows each release asset's digest), review the release's built-in extensions against `code-server/editor/extensions-kept` (the image tests fail on a listed one that is gone; a new one stays out until listed) and the Dockerfile's edits to the Markdown and git extensions (the build fails when one no longer matches), and run `tests/run-sidecar.sh code-server` and `scripts/code-server-e2e.sh --browser`.

## Upstream seams

These are listed in [CONTRIBUTING.md](../CONTRIBUTING.md#upstream-seams); every Lettuce upgrade checks them:

- `exec/` is built `FROM` the app-server's image (`additional_contexts: base: service:app-server`), so it depends on that image being Debian with `apt`, `bash` as root's shell, the image `ENV` that points `PATH`, `NPM_CONFIG_PREFIX`, `CARGO_HOME`, `GOBIN` and the `UV_*` variables at `/opt/agent-tools`, and `/usr/local/bin/agent-env` reading PID 1's environment (`init: true`; its own comment says "Cron only", and the editor's terminal is its second user); and on the workspaces at `$LETTA_STATE_DIR/workspaces` and the tools at `$LETTA_STATE_DIR/tools`, mounted as the app-server mounts them.
- The landing page's agent links depend on code-server's `?folder=` query and the workspaces at `/work/<agent-id>`.
