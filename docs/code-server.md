# Code editor

Each stack can have a code editor: VS Code in the browser ([code-server](https://github.com/coder/code-server)) on that stack's agent workspaces, at `https://<garden>/code-server/` (`<garden>` is the stack's garden address, `<name>-garden.<your-domain>`), behind the garden's Cloudflare Access sign-in. Browse and edit what the agents wrote, search, compare files, review and commit changes in Source Control, and use a terminal that has the agents' tools. It is opt-in, behind the `garden-code-server` profile. `lettucectl shell` and `toolbox` do the same for the operator on the host; this is the person-facing version.

```
browser --Access--> tunnel: <garden>/code-server/ --> code-server (the gate: Access JWT, prefix, headers, pages)
                                                        |  a Unix socket (no port, no network)
                                                     garden-code-server-editor (code-server: edits, runs nothing from the workspaces, no git)
                                                        |  code-exec network (internal), SSH
                                                     garden-code-server-exec (the terminal and git: the app-server's image and tools) --> internet
```

## For the person using it
1. **Open `https://<your garden>/`** and sign in as usual. Under "Code editor" it lists your agents, by the names Lettuce shows; each opens the editor in that agent's folder, `/work/<agent-id>`. Opening the page asks for a fresh list, which arrives within a minute, so a new agent shows up when you reload it.
2. **Or open the editor itself,** `https://<your garden>/code-server/`, and choose File -> Open Folder -> `/work/<agent-id>`. Keep to one agent per window; don't open `/work` itself.
3. **The editor stays in Restricted Mode, and that is on purpose.** The banner says so on every window. **Never choose "Trust" or "Trust Folder & Continue"**: agents write these folders, and a trusted folder can run their tasks and settings inside the editor, which shares its address with your vault and Gmail triggers. If you trusted one by mistake, open the Command Palette, run **Workspaces: Manage Workspace Trust** and choose **Don't Trust**, or clear the site's data in your browser.
4. **What works:** editing, search, compare, the built-in language support (TypeScript and JavaScript with the bundled TypeScript, JSON, HTML, CSS, and syntax highlighting for most languages), formatting with the built-in formatters, image previews, the Markdown preview (Open Preview to the Side), and Source Control (changes, diffs, staging, commits, branches). The preview shows images and formatting but runs no script and loads no frames, whatever the file holds; its security setting has no effect here. Source Control opens each repository without asking for trust: every git command it runs goes to the terminal's container (below), so the repository's hooks and config run there, never in the editor. A commit needs a name and email: set them once per repository in the terminal (`git config user.name ...`, `git config user.email ...`), since anything global is gone after a restart.
5. **The terminal** (Terminal -> New Terminal) opens in the folder you have open (in `/work` when that folder is not one of the workspaces, such as the editor's home, where File -> Open Folder starts), in a separate container with the agents' tools: the same image as the agents' shell, the workspaces and `/opt/agent-tools`. Use it for everything that runs code:
   - **git:** Source Control runs its git here too, so the terminal is always an alternative (`git status`, `git log`, `git rebase`). Pushing to a remote, from either, needs your credentials, which don't belong here: ask the operator (`lettucectl toolbox`).
   - **tests, builds, scripts:** `npm test`, `pytest`, `make`, as an agent would.
   - **debugging:** `node inspect`, `python -m pdb`, `dlv`. The editor has no debugger.
   - **formatters and linters beyond the built-in ones:** `npx prettier --write .`, `ruff format`, `npx eslint --fix`.
   - **installing tools:** `npm i -g`, `uv tool install`, `go install` and `cargo install` put them in `/opt/agent-tools`, shared with every agent of the stack. Anything else you install (`apt`, `pip` outside `uv`) is gone after the next restart.

   The terminal starts with a reminder: **`/work` and `/opt/agent-tools` are shared with every agent.** Never store a token or password there: no `npm login` or `cargo login`, no credentials in config files.
6. **Not available:** extensions (no marketplace, nothing can be installed), VS Code's Chat and other AI features (switched off: talk to your agents in Lettuce), the rich Markdown Editor (the preview stays), notebooks, the debugger, port forwarding of dev servers, Settings Sync and any sign-in to GitHub or Microsoft.

## For the operator
```bash
./lettucectl profiles <current list>,garden-code-server      # e.g. cloudflared,search,garden-code-server
```
- `profiles` routes `https://<garden>/code-server/` to the gate on every stack (on the garden's own address and Access application), and re-applies each stack's Access applications with an HttpOnly, SameSite=Lax cookie. `up` builds three images and starts three containers per stack: `garden-code-server` (the gate), `garden-code-server-editor` and `garden-code-server-exec` (the shell). The first build downloads code-server (pinned by version and SHA-256) and installs an SSH server on top of the app-server image. Dropping the profile removes the route and the containers; the editor's settings stay on the volume `lettuce-<name>_code-server-data`.
- Nothing new goes in `stack.env`. The editor creates the SSH keys between itself and the shell on first start, on its own volumes, and rewrites `authorized_keys` and `known_hosts` at every start.
- Editor state (settings, recently opened folders, the SSH client key) lives on `lettuce-<name>_code-server-data` and is not backed up: nothing in it is needed to restore a stack. The files people edit are the agents' workspaces, which `backup` copies.
- Logs: `./lettucectl logs <name> garden-code-server`, `garden-code-server-editor`, `garden-code-server-exec`.
- Moving code-server to a new release: change `CODE_SERVER_VERSION` and both `SHA256_*` in `code-server/editor/Dockerfile` (GitHub shows each release asset's digest), review the release's built-in extensions against `code-server/editor/extensions-kept` (the image tests fail on a listed one that is gone; a new one stays out until listed) and the Dockerfile's edits to the Markdown and git extensions (the build fails when one no longer matches), and run `tests/run-sidecar.sh code-server` and `scripts/code-server-e2e.sh --browser`.

## Security model
The editor shares its address (origin) with the vault and Gmail triggers: the stack's garden address, `<name>-garden.<your-domain>`, not Lettuce's. Whatever runs on that origin acts there as the person, and only the garden pages' own checks (Fetch Metadata, Cross-Origin-Opener-Policy, the form token) keep it from approving a vault request or changing a trigger. Lettuce's address is the same *site*, so Lettuce's SameSite=Lax sign-in cookies still go with requests from the editor's tab (see "What this does not cover" below). And code-server, by design, serves its webviews from its own origin, so any code in its extension host can open a page that runs there. So the design rests on one rule: **nothing an agent wrote ever runs in the editor's container.**

- **The editor never trusts a workspace.** VS Code runs tasks, debug sessions and a workspace's terminal settings only in a trusted workspace; there is no other switch for tasks, and `tasks.json` decides where a task runs. The editor's settings keep every workspace in Restricted Mode (no startup prompt, the banner always on) and allow three things there: the TypeScript extension, which then uses only its bundled TypeScript and bundled plugins (a workspace's own TypeScript, Node or `tsconfig` plugins need trust), terminals, which go to the shell container, and the git extension, whose git runs there too (below). The person can still choose "Trust" in a dialog (running a task asks); code-server keeps that choice in the browser, so the editor can't undo it. That is the one way left for agents' code to reach the editor, and why the guide above says never.
- **Nothing in the editor can run or install code.** Its image keeps an allow-list of code-server's built-in extensions (`code-server/editor/extensions-kept`): none that start processes or provide tasks (npm, grunt, gulp, jake, PHP validation, terminal suggestions, tunnels), no debugger, none that render workspace content in webviews (notebooks, the profile viewer, Simple Browser) but the Markdown preview, which is held to its Strict policy (no script but its own, no frames or objects; agents' HTML is shown, never run): the image pins it, so the preview's security picker can't turn the policy off, and removes the Markdown Editor, a richer webview VS Code itself opens in Restricted Mode only after an "Open Anyway"), none that sign in anywhere (Copilot, GitHub, Microsoft). There is no marketplace (`EXTENSIONS_GALLERY={}`), the extensions directory is read-only and empty, the image has no `node` on `PATH`, no git, no compilers and no shells for VS Code to offer as terminal profiles, and the fixed settings come back whole on every restart, with nothing added inside them. code-server reads only the image's own config file (`--config`), so no file on the editor's volume can turn on what `lettucectl check` refuses on the command line.
- **Source Control's git runs in the shell container.** A repository's own config runs code (`core.fsmonitor`, filters, `diff.external`, hooks), even for `git status`, which is why VS Code's git extension asks to trust each repository's folder before opening it; a trusted folder would also run its tasks and terminal settings in the editor. Here the extension's `git.path` is the fixed `/opt/lettuce-editor/bin/shell-git` (a machine setting, which a workspace can't change), which runs each git command over SSH in `garden-code-server-exec`, in the same folder (a command from outside `/work` runs in `/`, where there is no repository), where the repository's config runs with an agent's rights. The editor has no git of its own to fall back on. So the image removes that trust prompt from the extension (the build fails when a release's code no longer matches the edit), and the editor stays in Restricted Mode. What git prints (file and branch names, commit messages, diffs) is text agents wrote, shown by the workbench like file content (see "What this does not cover"). The extension also reads files under `.git` itself, in the editor; an agent could point one at an editor file with a symlink and have its contents passed to git in the shell, but the editor holds nothing secret (its SSH key logs in only to the shell). When Source Control cancels a git command (a newer `git status` replaces an older one), only the editor's side stops: the command itself still runs to the end in the shell.
- **Nothing reaches the editor but the gate.** code-server has no sign-in of its own here, so it listens on no port at all: only on a Unix socket on a volume that only the gate (read-only) and the editor mount. Its one network leads to the shell, and only the editor connects over it: the shell, where agents' code runs whenever you run it in the terminal, has nothing on the editor to connect to.
- **The terminal runs in the shell container.** Its profile is an SSH session into `garden-code-server-exec`, in the open folder, and so is the editor's login shell and `SHELL`, which VS Code falls back to when no setting names a profile (a new Settings Profile starts with none), through upstream's `agent-env` (so the agents' `PATH` and package managers apply). The shell is built on the app-server's image and mounts the workspaces and `/opt/agent-tools` as the app-server does: it is as strong as an agent and holds nothing an agent can't get. No Access token, no Google token, no credentials, not the stack network (it can't reach Lettuce, the vault or the other sidecars), and only the editor can log in (key login; the editor holds the client key on its own volume). It can reach the internet, directly: pipelock does not cover it.
- **The gate is the only way in.** Every request and WebSocket under `/code-server/` needs a verified Access JWT of the garden's application, the same check the vault makes; WebSockets also need the garden's own `Origin` and close when the sign-in expires (code-server reconnects, which needs a current sign-in), and anything but a read must come from the garden's own pages (`Sec-Fetch-Site: same-origin`): your other stacks share the sign-in cookie's site, not its origin. The gate passes on only listed headers: the editor never sees the Access token, the Access cookie or Lettuce's session cookie, and can never set a cookie, an opener policy, or a service worker scope wider than `/code-server/`. Only the workbench and code-server's own frames may load as pages; every other response (an agent's HTML or SVG file, say) is served `nosniff` with `Content-Security-Policy: sandbox`, so it can't become a page on the origin, and every answer varies with how it was requested (`Vary: Sec-Fetch-Dest`), so the browser's cache never hands a file to a page load the gate refused. The port proxy is off.
- **The editor is not on Lettuce's address.** The garden has its own (`<name>-garden.<your-domain>`), so script in the editor's tab can't read Lettuce's pages, and Lettuce's WebSocket, which carries everything an agent does, accepts only Lettuce's own origin.
- **The garden pages refuse same-origin script.** The editor shares the garden's address with the vault and Gmail triggers. Their pages and the garden's landing page load only as top-level pages and take form posts only from their own pages (Fetch Metadata), and open cut off from the editor's tab (Cross-Origin-Opener-Policy). The Access cookies are HttpOnly, so no script can read a sign-in token and hand it to an agent. The landing page runs no script.
- **The landing page shows text agents can write.** With the code editor on, even alone, the garden executor runs every minute as root in the app-server to send the agents' names to the landing page. Agents are root there too and can read its token, so they can send names of their own: the page shows them as escaped text, cut to 200 characters, and links only to ids shaped like agent ids.
- **What this does not cover.** A bug in code-server or in a kept built-in (rendering crafted file content, terminal or git output, or a TypeScript hover) could still run script in the editor's tab. There it acts on the garden's address as the person, where the checks above guard the vault and Gmail triggers. The garden and Lettuce are the same *site*, so the browser still sends Lettuce's sign-in cookie with requests from that tab: script there could send Lettuce's HTTP API requests it can't read the answers to. Whether that API refuses them (it checks the origin only on WebSockets) is upstream's to change. code-server's pin is kept current for these reasons.
- `lettucectl check` refuses a stack where any of the three containers loses its hardening, networks or mounts, where another service joins their networks or network namespaces or mounts their volumes, where the editor listens on a port, or runs with the port proxy, extensions, a marketplace, another settings directory or anything that switches trust off (each flag that matters once, since code-server takes the last), or where the shell joins the stack network or keeps `NET_RAW`.

### Checking it
`scripts/code-server-e2e.sh --browser` (Docker, the app-server image, and the internet for the first build) runs the real images and drives the workbench in Chromium: it plants what an agent could in a workspace (a terminal profile, an automatic task, its own TypeScript and `tsserver` node, a `tsconfig` plugin, `git.path`, a repository with a `core.fsmonitor` and a pre-commit hook), opens the folder, a TypeScript file and a terminal, types a command, commits a change from Source Control and asks to run a task. Opening the folder, the terminal and Source Control and committing must ask nothing; nothing planted may run in the editor; what is typed, the repository's `fsmonitor` and its hook must run in the shell; running a task must ask for trust.
