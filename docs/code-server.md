# Code editor

Each stack can have a code editor: VS Code in the browser ([code-server](https://github.com/coder/code-server)) on that stack's agent workspaces, at `https://<lollo>/code-server/` (`<lollo>` is the stack's lollo address, `<name>-lollo.<your-domain>`), behind the lollo's Cloudflare Access sign-in. Browse and edit what the agents wrote, search, compare files, review and commit changes in Source Control, and use a terminal that has the agents' tools. It is opt-in, behind the `lollo-code-server` profile. `lolloctl shell` and `toolbox` do the same for the operator on the host; this is the person-facing version.

![Browser, Cloudflare Access, the gate, the editor that runs nothing, the shell that runs code, and the workspaces](diagrams/code-server-flow.svg)

An interactive version, [code-server-flow.html](diagrams/code-server-flow.html), opens in a browser from a clone of this repo.

How the code editor is built and wired, for developers: [code-server/README.md](../code-server/README.md).

## Using it
1. **Open `https://<your lollo>/`** and sign in as usual. Under "Code editor" it lists your agents, by the names Lettuce shows; each opens the editor in that agent's folder, `/work/<agent-id>`. Opening the page asks for a fresh list, which arrives within a minute, so a new agent shows up when you reload it.
2. **Or open the editor itself,** `https://<your lollo>/code-server/`, and choose File -> Open Folder -> `/work/<agent-id>`. Keep to one agent per window; don't open `/work` itself.
3. **The editor stays in Restricted Mode, and that is on purpose.** The banner says so on every window. **Never choose "Trust" or "Trust Folder & Continue"**: agents write these folders, and a trusted folder can run their tasks and settings inside the editor, which shares its address with your vault and Gmail triggers. If you trusted one by mistake, open the Command Palette, run **Workspaces: Manage Workspace Trust** and choose **Don't Trust**, or clear the site's data in your browser.
4. **What works:** editing, search, compare, the built-in language support (TypeScript and JavaScript with the bundled TypeScript, JSON, HTML, CSS, and syntax highlighting for most languages), formatting with the built-in formatters, image previews, the Markdown preview (Open Preview to the Side), and Source Control (changes, diffs, staging, commits, branches). The preview shows images and formatting but runs no script and loads no frames, whatever the file holds; its security setting has no effect here. Source Control opens each repository without asking for trust: every git command it runs goes to the terminal's container (below), so the repository's hooks and config run there, never in the editor. A commit needs a name and email: set them once per repository in the terminal (`git config user.name ...`, `git config user.email ...`), since anything global is gone after a restart.
5. **The terminal** (Terminal -> New Terminal) opens in the folder you have open (in `/work` when that folder is not one of the workspaces, such as the editor's home, where File -> Open Folder starts), in a separate container with the agents' tools: the same image as the agents' shell, the workspaces and `/opt/agent-tools`. Use it for everything that runs code:
   - **git:** Source Control runs its git here too, so the terminal is always an alternative (`git status`, `git log`, `git rebase`). Pushing to a remote, from either, needs your credentials, which don't belong here: ask the operator (`lolloctl toolbox`).
   - **tests, builds, scripts:** `npm test`, `pytest`, `make`, as an agent would.
   - **debugging:** `node inspect`, `python -m pdb`, `dlv`. The editor has no debugger.
   - **formatters and linters beyond the built-in ones:** `npx prettier --write .`, `ruff format`, `npx eslint --fix`.
   - **installing tools:** `npm i -g`, `uv tool install`, `go install` and `cargo install` put them in `/opt/agent-tools`, shared with every agent of the stack. Anything else you install (`apt`, `pip` outside `uv`) is gone after the next restart.

   The terminal starts with a reminder: **`/work` and `/opt/agent-tools` are shared with every agent.** Never store a token or password there: no `npm login` or `cargo login`, no credentials in config files.
6. **Not available:** extensions (no marketplace, nothing can be installed), VS Code's Chat and other AI features (switched off: talk to your agents in Lettuce), the rich Markdown Editor (the preview stays), notebooks, the debugger, port forwarding of dev servers, Settings Sync and any sign-in to GitHub or Microsoft.

## Running it
```bash
lolloctl profiles <current list>,lollo-code-server      # e.g. cloudflared,search,lollo-code-server
```
- `profiles` routes `https://<lollo>/code-server/` to the gate on every stack (on the lollo's own address and Access application), and re-applies each stack's Access applications with an HttpOnly, SameSite=Lax cookie. `up` builds three images and starts three containers per stack: `lollo-code-server` (the gate), `lollo-code-server-editor` and `lollo-code-server-exec` (the shell). The first build downloads code-server (pinned by version and SHA-256) and installs an SSH server on top of the app-server image. Dropping the profile removes the route and the containers; the editor's settings stay on the volume `lollo-<name>_code-server-data`.
- Nothing new goes in `stack.env`. The editor creates the SSH keys between itself and the shell on first start, on its own volumes, and rewrites `authorized_keys` and `known_hosts` at every start.
- Editor state (settings, recently opened folders, the SSH client key) lives on `lollo-<name>_code-server-data` and is not backed up: nothing in it is needed to restore a stack. The files people edit are the agents' workspaces, which `backup` copies.
- Logs: `lolloctl logs <name> lollo-code-server`, `lollo-code-server-editor`, `lollo-code-server-exec`.

## Security model
The editor shares its address with the vault and Gmail triggers: the stack's lollo address, `<name>-lollo.<your-domain>`, not Lettuce's. Whatever runs in the editor's tab acts there as you. So the design rests on one rule: **nothing an agent wrote ever runs in the editor's container.** Everything that runs code goes to a separate container, the shell, which is exactly as strong as an agent.

- **The editor never trusts a workspace, and you shouldn't either.** It keeps every folder in Restricted Mode, where VS Code runs no tasks, no debugger and no workspace terminal settings. You can still choose "Trust" in a dialog (running a task asks), and the browser remembers that choice, so the editor can't undo it. That is the one way left for agents' code to reach the editor: **never trust a folder.**
- **Nothing in the editor can run or install code.** There is no marketplace and no extension to install; only a short list of VS Code's built-in extensions is kept: none provides tasks, debugs, runs a workspace's own code or signs in anywhere, and the TypeScript support uses only its bundled TypeScript, never a workspace's. The Markdown preview shows agents' HTML but never runs it.
- **Source Control's git runs in the shell, not the editor.** A repository's own config and hooks can run code even for `git status`; here they run in the shell with an agent's rights. What git prints (file and branch names, commit messages, diffs) is text agents wrote. The git extension also reads files under `.git` itself, in the editor: an agent could point one at an editor file with a symbolic link and have its contents passed to git in the shell, but the editor holds nothing secret (its SSH key logs in only to the shell). When Source Control cancels a git command, only the editor stops waiting: the command still runs to the end in the shell.
- **The terminal is the shell, as strong as an agent and no stronger.** It has the agents' tools and the workspaces, and nothing else: no sign-in token, no Google token, no credentials, and no way to Lettuce, the vault or the other lollo pages. It reaches the internet directly: pipelock does not cover it.
- **Only your signed-in browser reaches the editor.** Every request needs your sign-in to the lollo's Access application, the same check the vault makes, and the editor never sees your sign-in token or Lettuce's cookies. Files agents wrote (an HTML or SVG file, say) are never served as pages.
- **The editor is not on Lettuce's address.** The lollo has its own (`<name>-lollo.<your-domain>`), so script in the editor's tab can't read Lettuce's pages, and Lettuce's WebSocket, which carries everything an agent does, accepts only Lettuce's own origin.
- **The lollo pages refuse same-origin script.** The editor shares the lollo's address with the vault and Gmail triggers. Their pages and the lollo's landing page load only as top-level pages and take form posts only from their own pages (Fetch Metadata), and open cut off from the editor's tab (Cross-Origin-Opener-Policy). The Access cookies are HttpOnly, so no script can read a sign-in token and hand it to an agent. The landing page runs no script.
- **The landing page shows text agents can write.** With the code editor on, even alone, the lollo executor runs every minute as root in the app-server to send the agents' names to the landing page. Agents are root there too and can read its token, so they can send names of their own: the page shows them as escaped text, cut to 200 characters, and links only to ids shaped like agent ids.
- **What this does not cover.** A bug in code-server or in a kept built-in (rendering crafted file content, terminal or git output, or a TypeScript hover) could still run script in the editor's tab. There it acts on the lollo's address as the person, where the checks above guard the vault and Gmail triggers. The lollo and Lettuce are the same *site*, so the browser still sends Lettuce's sign-in cookie with requests from that tab: script there could send Lettuce's HTTP API requests it can't read the answers to. Whether that API refuses them (it checks the origin only on WebSockets) is upstream's to change. code-server's pin is kept current for these reasons.
- `lolloctl check` refuses to start a stack where the editor, the gate or the shell has lost any of this isolation.

How each of these is enforced, and how it is tested: [code-server/README.md](../code-server/README.md#rules).
