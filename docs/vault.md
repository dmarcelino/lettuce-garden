# Vault

Each stack can have a personal vault of secrets, with Bitwarden's item types: logins, cards, identities (name, address, email, phone, ID numbers), secure notes and SSH keys, each with its own fields, plus custom fields. A Bitwarden export imports as is. Agents can ask to use a secret, for example to fill in a delivery form or write a letter, and the person decides. By default an agent never reads the values it uses: it writes placeholders such as `{{VAULT_POSTAL_CODE}}`, and the values replace them only at the last step, in the file or command, so they don't reach the AI provider. The vault is encrypted with a passphrase only that person knows. It is opt-in, behind the `garden-vault` profile.

![An agent asks the vault, you approve or deny, and the agent gets a handle for vault-run, or with a reason the values](diagrams/vault-flow.svg)

An interactive version, [vault-flow.html](diagrams/vault-flow.html), opens in a browser from a clone of this repo.

How the vault is built and wired, for developers: [vault/README.md](../vault/README.md).

## Using it
1. **Open `https://<your garden>/vault/`** and sign in as usual; `<your garden>` is your stack's garden address, `<name>-garden.<domain>`. Its home page, `https://<your garden>/`, links to it too.
2. **Create your vault:** choose a passphrase of at least 12 characters. Four or five unrelated words work well. **Nobody can recover it**, not even whoever runs the server. If you forget it, you have to erase the vault and start again (step 7).
3. **Add secrets:** go to **Secrets**, then **Add a secret**, and pick a type, or **Import from Bitwarden** (below). Every secret has a name. Fields in *italics* are private; the others agents can read, like the name. Every field is optional, but a secret needs at least one.

   | Type | Fields | Can be used without asking |
   |---|---|---|
   | Login | username, *password*, *authenticator key (TOTP)*, websites, *notes* | no, always asks |
   | Card | cardholder name, brand, *number*, *expiration month*, *expiration year*, *security code*, *notes* | no, always asks |
   | Identity | title, first, middle and last name, *username*, *company*, *Social Security number*, *passport number*, *license number*, *email*, *phone*, *address 1-3*, *city*, *state / province*, *postal code*, country, *notes* | the address fields, if you choose; the rest always asks |
   | Secure note | *notes* | yes, if you choose |
   | SSH key | *private key*, public key, fingerprint, *notes* | no, always asks |

   - **Custom fields:** any secret can also have up to 20 fields you name yourself (a PIN, a VAT ID, a member number). They are always private and always ask. Agents ask for one by its name in lower case, with `_` for spaces and symbols: "VAT ID" is `vat_id`.
   - **Private fields** stay hidden on screen until you press **Show private fields**, which is recorded in History, and an agent gets them only when you agree.
   - **Name:** give each secret a name you and your agents will recognise, such as "Home address" or "Work Visa".
   - **"What agents may use it for":** an optional note that agents see, for example "online shopping deliveries".
   - **Import from Bitwarden:** in Bitwarden, export your vault choosing the **.json** format (not the encrypted one), then on **Secrets** press **Import from Bitwarden** and upload it (up to 5 MB). Logins, cards, identities, secure notes and SSH keys come in with their custom fields; folders, passkeys, attachments and password history are left out. Every imported secret asks before an agent uses it. A field the vault can't keep (longer than 4000 characters, a custom field whose name it can't use or already has, a custom field beyond the 20th) is left out, not its item. The page lists what was imported and what was left out and why. The file is read in the vault's memory and not kept; delete it from your device afterwards, since it holds everything unencrypted. Importing twice makes copies.
   - **Upgrading from the first vault:** secrets saved before these types existed (the free-text Address, Company and Note, and the old Membership, ID document, Payment card and Login) are deleted the first time the vault is unlocked after the upgrade, and History records how many. Add them again, or import them from Bitwarden.
4. **Get notified:** on your phone, add the page to the Home Screen (on iPhone: Share, then Add to Home Screen), open it from there, go to **Notifications**, then **Enable on this device**.
5. **Answer requests:** when an agent asks for something, a notification arrives, and the agent is told to post the request's link in the chat too, so you can answer without notifications. The request shows the secret, the private fields the agent wants and the purpose it gave. Normally it also says the values go to a command or file the agent prepared, so they won't appear in the conversation. When the agent asked to **read** the values instead, the request says so in a warning, with the reason it gave: approve that only when the reason convinces you. Untick anything it doesn't need, then press **Share once** or **Deny**. Agents are told to keep checking until you answer (a request expires after 10 minutes); if one stopped without picking up your answer, send it any message in the chat and it collects it. **Requests** lists what is waiting and what you answered recently; **History** lists everything.
6. **Locking:** the vault locks when the server restarts, after 12 hours without you using the page, or when you press **Lock**. While it is locked, agents get nothing and you get a notification asking you to unlock.
7. **Forgot the passphrase:** on the unlock page, under **Forgot your passphrase?**, type `DELETE` and press **Erase in 24 hours**. Every device with notifications on is told. 24 hours later every secret and the history are deleted, and the vault asks you to create a new one. The page shows the time with its time zone and how long is left. Until then, unlocking the vault or pressing **Cancel the erase** stops it. With the vault unlocked, **Settings -> Erase the vault** erases it at once instead.

**Connect your agents:** agents find the vault through Lettuce's **Settings -> MCP**, as an HTTP server named `vault` with URL `http://garden-vault:8000/mcp`. `lettucectl add` puts it there for a new stack; for a stack that existed before, the operator runs `./lettucectl mcp <name>` (see [Running it](#running-it)), or you add it there by hand. lettucectl does this once per stack: if you remove the server in Settings -> MCP, it stays removed. Registering it gives agents nothing new: they can already reach that address over the stack's network, and approving still happens only in the vault.

### Placeholders: values the agent never reads
Everything in an agent's conversation goes to the AI provider, so by default (`delivery: "placeholders"`) an agent doesn't get the values at all. It prepares the work with placeholders, such as `{{VAULT_ADDRESS1}}` in a letter, `{{VAULT_POSTAL_CODE}}` in an email's text or `$VAULT_NUMBER` in a form-filling script, and once you approve, it gets a **handle** instead of the values. At the last step it runs `vault-run`, a helper that `lettucectl skills` installs with the `using-vault-secrets` skill: `vault-run` trades the handle for the values, gives them to one command as `VAULT_<FIELD>` environment variables, and replaces them with `[VAULT_<FIELD>]` in the command's output (values of 6 characters or more; also a card number printed with spaces or dashes). That command can be the agent's own script, or `vault-fill`, which copies a template with the placeholders filled in: a document (text, Markdown, HTML, JSON, Word, Excel, PowerPoint or OpenDocument; for a PDF, the agent fills the source and converts the copy), or the arguments of an MCP call, such as sending an email, which `vault-fill` pipes straight into the call. One `vault-run` can take several handles, for a letter with two addresses; the agent then gives each request an `alias`, so the placeholders become `{{VAULT_HOME_CITY}}` and `{{VAULT_CLIENT_CITY}}`. The handles are used together or not at all: when one has expired, or two would set the same name, none is used up and the command doesn't run. A handle works once, for 5 minutes, and History records when it is used. This keeps values out of the conversation; it does not stop a misled agent (see [Security model](#security-model)).

An agent that needs to understand a value itself, not only place it, can ask with `delivery: "text"`, but only with a reason, which the request page shows you in a warning. Agents are told to check the public details first (an identity's country, a card's brand) and to ask for the fewest fields.

## Running it
- **Turn it on:**
  ```bash
  ./lettucectl profiles <current list>,garden-vault      # e.g. cloudflared,search,garden-vault
  ```
  This routes `https://<garden>/vault/` (and the garden's home page, linking to the garden features that are on) to the vault on every stack, on the stack's garden address and its own Access application, then builds and starts it. Each stack gets its own push keys for the vault (`VAULT_VAPID_*` in `stack.env`). Dropping `garden-vault` from the list removes the route and the container, and leaves the data where it is.
- **Register it with the agents:**
  ```bash
  ./lettucectl mcp all      # adds the vault (and, with garden-doc-tools, office and pdf) to each Settings -> MCP
  ```
  `add` does this for a new stack, and `profiles` prints, for each stack, whether it is registered or the entry to add by hand. `mcp` adds `{"name": "vault", "transport": "http", "url": "http://garden-vault:8000/mcp"}` once per stack (`VAULT_MCP_REGISTERED` in `stack.env`), so a person who removes it keeps it removed; `mcp <name> --force` adds it again. An HTTP entry with that exact URL counts as the vault whatever its name, so one added by hand is not added twice; a different server named `vault` is left alone, and nothing is added (it says so). It writes only that one entry, then restarts the stack's BFF alone so agents see it (the vault and the app-server keep running; see [doc-tools.md](doc-tools.md#turning-it-on) for how the list is written and what can undo it). With `garden-vault` dropped from the list, `up` and `profiles` remove the entry they registered, since an HTTP server that does not answer makes every `letta mcp tools` call fail; if that fails, the next `up` or `profiles` retries it.
- **Data:** the vault lives in the Docker volume `lettuce-<name>_vault-data`, not under `stacks/<name>/`. `lettucectl backup` includes it (see [operations.md](operations.md#backups)). The backup is useless without the passphrase.
- **Removal:** `lettucectl remove <name>` deletes the volume, so removing a stack deletes its vault, also after the `garden-vault` profile was turned off. It says so before asking for confirmation whenever the volume exists.
- **Forgotten passphrase:** there is no recovery. The person can erase the vault from the unlock page, which runs 24 hours later (step 7 above); the time is kept in the vault's file, so a restart does not lose it. An erase that came due while the server was down waits one more hour after it starts, and every device is told, so the person still gets a chance to stop it. A person can ask for an erase at most 3 times an hour, since each request notifies every device. To erase it at once instead, delete the volume (see the troubleshooting table in [operations.md](operations.md#troubleshooting)).
- **Isolation:** the vault container has a read-only root filesystem and no capabilities, runs as a non-root user and has no host mounts. Its volume is mounted by nothing else. The containers agents run in, and those sharing their network, drop `NET_RAW`, so agents cannot capture the Access token on its way to Lettuce. `lettucectl check` refuses a stack where any of that is not true.

## Security model
What the vault protects, and what it does not.

- **The vault file is encrypted.** Each secret is encrypted with AES-256-GCM using a random data key. That key is stored only wrapped with a key derived from your passphrase (scrypt, 128 MiB). Secret names, fields and the history details are all encrypted. Someone who copies the vault file or a backup sees only secret ids, types and timestamps, and can only try guessing your passphrase, which scrypt makes slow.
- **The key is only in memory:** from when you unlock until you lock, the 12-hour auto-lock, or a restart. Agents asking for secrets do not keep the vault open.
- **Agents never get a private value without your say-so:**
  - Every page, every unlock and every approval requires your Cloudflare Access sign-in, which the vault itself checks. Agents can reach the vault service but cannot sign in as you. Your sign-in token also passes, unencrypted, through the network the agents share with Lettuce; `lettucectl` takes away the capability they would need to read that traffic, and `check` refuses a stack that has it. While Lettuce's web server restarts and the agents keep running, an agent could take its place and receive Lettuce's sign-in token, but the vault accepts only the garden's.
  - Pages load only as pages, and forms post only from the vault's own pages, which the browser vouches for (Fetch Metadata). A script running on the same address (the garden's, which the code editor shares) or on Lettuce's can't read a page's form token or approve anything; opening a vault page from such a tab cuts it off from that tab (Cross-Origin-Opener-Policy). The Access sign-in cookie is HttpOnly, so no script can read your sign-in token either.
  - Agents cannot add, change or delete secrets.
  - Logins, cards, SSH keys, custom fields and an identity's username, company, ID numbers, email and phone always ask. A secure note's text and an identity's address fields ask unless you switch that secret to "Agents may use ... without asking"; a request that also wants a field that always asks waits for you as a whole.
  - Public fields (a login's username and websites, a card's cardholder name and brand, an identity's title, names and country, an SSH key's public key and fingerprint) and the name are visible to agents, so they can pick the right secret.
- **A value shared as text is in the conversation.** The AI provider sees it, and Lettuce stores the conversation unencrypted on the server. That is why placeholders are the default, and why text needs a reason you read. Share only what the task needs.
- **Agents are told not to repeat what you share.** The values come with rules: use them only for the purpose you approved, send them to no outside service (a search, a map, an address checker) unless that purpose needs it, and never write them back in a reply, memory or files, not even to confirm them. Asked to check an address, an agent should say what it checked and the result, not the address. These are instructions the agent follows, not something the vault can enforce.
- **Values passed with placeholders stay out of the conversation**, so the AI provider and the stored chat don't get them. That keeps a well-behaved agent from leaking them by accident; it is a precaution, not a guarantee. It does **not** stop an agent that has been misled, for example by a web page it read: it can redeem the handle itself, open the filled file, print a short value (a postal code, a security code) that `vault-run` doesn't hide, or have the command send the value somewhere. A filled document or email also goes wherever the agent puts it, and the AI provider may see it later if the agent reads it. Approving stays the decision that matters; read the purpose and approve only what fits it.
- **The vault doesn't protect against a determined administrator:** someone with root on the server can read the vault service's memory while it is unlocked, or change its code. What it does stop is someone browsing the server's files or backups.
- **Anyone who can sign in to your garden can erase a locked vault, after 24 hours.** The erase needs no passphrase, since the person who asks for it has usually forgotten it. The delay and the notifications are what protect you: every device with notifications on hears of it at once, and unlocking or cancelling stops it. Turn notifications on, or a sign-in someone else holds (a shared computer, a stolen session) could erase your vault while you aren't looking. An erase only deletes: nobody gets a value out of it.
- **Cloudflare sees your passphrase in transit,** as it sees all traffic to your Lettuce stack.

## Limits
- At most 5 requests can wait at once. A request expires after 10 minutes, and shared values wait 30 minutes for the agent to collect them. A handle works once, within 5 minutes of the agent receiving it, and an agent can hold at most 10 unused handles. Locking the vault cancels every handle and every shared value the agent has not collected yet.
- Requests that are waiting are forgotten when the vault restarts. The agent simply asks again.
- iOS delivers notifications only to web apps added to the Home Screen, and only on iOS 16.4 or later.
